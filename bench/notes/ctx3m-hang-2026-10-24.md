# 3M 上下文把整机跑挂：2026-10-24 一次静默卡死的完整取证

> 本文是**过程性工程笔记**，不是客户文档。对外结论另写进 `docs/`。
> 数据件：`bench/data/2026-10-24_b65-32g-q4_0-ctx3m-probe.json`（事故）与
> `bench/data/2026-10-24_b65-32g-q4_0-ctx262144-single-ctrl.json`（对照组）。

---

## 0. 一句话

**不是 GPU 挂了，是主机内存被顶穿。** 3M 上下文（`-c 3145728 --parallel 12`）把两卡显存吃到各剩
0.19 GiB，长 prompt 的 prefill 要临时计算缓冲时分配失败，SYCL / Level Zero 的失败路径**不报错、
退化成重试**，重试又把主机提交内存继续往上顶——进程私有内存 73 GB、整机提交 91.79 / 95.11 GiB
（96.6%），最后内核也分配不出内存，**整机静默卡死，无蓝屏、无 minidump、无 WATCHDOG dump**。

## 2. 判据：为什么不是 GPU TDR

先数转储文件，这是唯一硬判据：

| 证据 | 结果 | 说明 |
| --- | --- | --- |
| `LiveKernelReports\WATCHDOG\*.dmp` | **无新增**（最新仍是 10-21 13:52） | GPU 引擎超时会在这里留 dump |
| `C:\Windows\Minidump\*.dmp` | **无新增**（最新仍是 10-23 19:49 的 `0x101`） | 蓝屏才会写 |
| WER `BlueScreen` / `LiveKernelEvent` | **无新报告** | 连错误报告都没生成 |
| Kernel-Power 41 | 有（17:01:19） | 非正常断电/重启 |

对比历史：这台机器 10-21 至 10-23 的 **5 次 `0x116`（VIDEO_TDR_ERROR）+ 1 次 `0x101`**
**全都有 minidump、全点名 `igdkmdnd64.sys`**，那才是 GPU 超时那条路。
`TdrDelay` 已经是 60 s，GPU 挂 60 s 内必出 `0x116` + minidump——这次什么都没有。

→ **判读顺序（写进 SOP）**：先数 WATCHDOG 时间戳与 minidump。
**有** → GPU 挂，走 TDR 归因；**没有、只有 Kernel-Power 41** → 内存提交顶穿，去看
`Committed Bytes / Commit Limit`。

| 显存余量 | 0.19 / 0.22 GiB | 9.68 GiB |

**同一个模型、同一条 prompt、同一个 llama.cpp、同一套参数**，只有 `-c` / `--parallel` 这一档不同。
→ 变量就是 3M 这一档的分配，单变量对照成立。**不是 prompt 太大、不是模型问题、不是 flash-attn 问题。**

## 4. 根因链（四步）

1. **3M 上下文的显存账没有余量**：KV q8_0 占 43.59 GiB，两卡各剩 0.19 / 0.22 GiB。
   这是 10-23 容量记录里就量到的（`p12` 用例），当时只记了「起得来」。
2. **prefill 到 8192 token 时要临时计算缓冲**：flash attention 的工作区随 prompt 长度涨，
   剩下的 0.19 GiB 装不下 → 分配失败。
3. **SYCL / Level Zero 的失败路径不报错**：llama-server 没有退出、没有 `OUT_OF_DEVICE_MEMORY`、
   没有 `DEVICE_LOST`，而是退化成重试 → GPU 空转、CPU 空转、日志静默。
4. **重试把主机侧顶穿**：Windows 把设备内存映射算进进程提交量，进程私有内存一路推到 73 GB，
   整机提交 91.79 / 95.11 GiB。到这个位置，**内核自己也要分配内存**（页表、IO、中断处理），
   分配不出 → 整机挂，且挂得干净利落，连 dump 都来不及写。

## 5. 页面文件 64 GB 是帮凶

| 项 | 值 |
| --- | --- |
| 物理内存 | 31.11 GiB |
| `e:\pagefile.sys` | 初始 65536 MB / 最大 131072 MB（**手动配置，非系统管理**） |
| commit limit | **95.11 GiB** |
| 3M 档实际提交 | 91.79 GiB（96.6%） |

**这是整件事最反直觉的一点**：页面文件本来是「32 GB 环境的硬性交付项」，但 64 GB 的页面文件让
Windows 敢承诺 95 GiB。于是本该是「进程分配失败 → llama-server 报 OOM → 自己退、机器照常用」
的场景，变成了「系统一直点头 → 直到内核也分不出 → 整机卡死要手动重启」。

**页面文件不是越大越好，是「够用且留余量」。**

→ 「够用」到底是多少？§5.1 定过 32 GB、§5.1.1 定过 64 GB，**两次都不对**。最终答案在 **§5.2：96 GB 固定**。

### 5.1 终局验证（20:31 改 32/32 后）：虚拟内存设多少稳当

> ⚠️ **本节「32 GB 固定」的结论已被 §5.2 取代**。它对 llama.cpp 那条路径有效（3M 装载变成干净自退），
> 但 32 GB 会把 H3 出视频挡死。最终定的是 **96 GB 固定**，3M 的闸改成 Job Object 限额。本节保留作过程记录。

两步实测把这条线收掉了：

| 页面文件配置 | commit limit | 3M 装载结果 | 提交峰值 |
| --- | --- | --- | --- |
| 初始 32 GB / 最大 64 GB（20:30 验证） | 63.11 → **被扩到 86.97 GiB** | 分配成功，埋着 17:00 同款风险 | **98.9%** |
| **初始 32 GB / 最大 32 GB**（21:52 验证） | **63.11 GiB，全程没扩** | **20.4 s 时 SYCL 报 `alloc FAILED: 16320 MiB`（KV buffer），llama-server 自己报 model loading error 干净退出** | **55.4%（34.99 GiB）** |

结论（写进 SOP）：

- **虚拟内存 = 初始与最大都设 32768 MB（32 GB 固定）**，落在 `e://pagefile.sys`。
  「初始小 + 最大大」等于没锁——Windows 压力下照样扩，扩回去就是 17:00 卡死的路。
- 锁死之后，3M 这一档的失败形态从「整机卡死要手动重启」变成「**进程报 OOM 自己退、机器照常用**」：
  装载 20.4 s 退出、提交峰值只到 55%、监控全程 450 个采样 limit 纹丝不动、无任何 dump。
- 32 GB 物理 + 32 GB 页面文件 = commit limit 63.11 GiB，是这套交付配置的硬天花板。
  超过它的请求（3M 档）llama-server 起不来，**这是设计行为不是故障**。
- 对外口径不变：可用上限 = 单卡 1M / 双卡默认 1.75M；3M 只作「分配上限」历史记录。

#### 5.1.1 🔴 32 GB 固定会挡住 H3 出视频（同一晚实测）

定案 32/32 之后跑 B65 H3 出视频，**720p / 1080p / 1440p 三档全部起不来**：

| 项 | 值 |
| --- | --- |
| 失败点 | `UNETLoader → safetensors.safe_open`，读 19.53 GB 的 DiT |
| 报错 | `OSError: 页面文件太小，无法完成操作。 (os error 1455)` |
| 失败时长 | 71.3 / 71.6 / 75.8 s（三档一致） |
| 失败时显存 | 16.54 GiB（文本编码器 14 960.20 MB 已 loaded completely 上卡） |
| commit 峰值 | **57.21 / 63.11 GiB（90.6%）**，166 个 2 s 采样 |
| GPU | 占空比 0%、整卡 45 W —— 还没开始算 |

**关键判据：与分辨率无关。** 三档同一处失败、同一显存占用、同一 commit 峰值 →
瓶颈是「读 19.53 GB DiT 要一份 commit 保障」，不是视频尺寸。

📐 **需求量估算**：失败时已用 57.21 GiB，DiT 19.53 GB 还要再要一份 → 实际需求约 **77 GiB**。
32 GB 物理 + 32 GB 页面文件 = 63.11 GiB，不够。

❌ **48 GB（49152）实测不够**：commit limit 79.11 GiB 下，H3 出视频 1920×1088 三次 + 864×480 一次
**全部 `0xC0000005`** 崩在 `load_torch_file` 的 safetensors 映射访问，而崩前 commit 只用 73%（57.76/79.11）
→ **不是 commit 顶穿，是映射读不进来**。举证与对照见
`bench/data/2026-10-24_b65-32g-h3-video-pf48-fail.json`。

✅ **页面文件定值改为 64 GB（65536 MB，初始 = 最大）**：这是 2026-10-21 实测跑通
480p / 720p / 1080p 三档时的配置（环境已逐项核对一致：同 torch、同 omni 内核、同 VRAM/RAM）。
commit limit 95.11 GiB。
⭐ **不再靠「页面文件设小」拦 3M** —— 那道闸改成 `--job-commit-gib`（Job Object 内核硬限额），
实测 3M 在 48 GB 配置下 18.0 s 干净自退。页面文件只负责「够装」，防护交给 job 限额。
（Windows 增大页面文件不必重启，改完立即生效 —— 21:4x 实测。）

⚠️ **产品页 §6 的视频数字是 64 GB 页面文件（e: 65536/131072）下测的**，32 GB 固定配置下不可复现
→ 产品页测试条件必须写页面文件值。数据件 `bench/data/2026-10-24_b65-32g-h3-video-pf32-fail.json`。
- 数据件：`2026-10-24_b65-32g-q4_0-ctx3m-loadonly-pfmax64.json`（旧配置对照）、
  `2026-10-24_b65-32g-q4_0-ctx3m-loadonly-pf3232.json`（32/32 终局）。

### 5.2 🔴 页面文件阶梯与定稿（22:05 至 22:45 复测）

5.1.1 把页面文件定成 64 GB 固定，**这一步是错的**。依据是「10-21 用 64 GB 跑通过三档」，
但 10-21 的实际配置是 `e: 65536 / 131072`（初始 64 GB、上限 128 GB）——
**页面文件当时被系统自己扩到了约 96 GB**，跑通三档的是那个 96 GB，不是 64 GB。

| 页面文件 | 提交上限 | 1920×1088 结果 | 提交峰值 |
| --- | ---: | --- | ---: |
| 32 GB（32768） | 63.11 GiB | 71.3 s 报 `os error 1455` | 57.21（90.6%） |
| 48 GB（49152） | 79.11 GiB | `0xC0000005` 崩在映射读，4/4 | 57.76（73%） |
| 64 GB（65536） | 95.11 GiB | 装载爬到 **92.08** 仍未见顶，余额 3 GiB，看门狗中止 | 92.08（96.8%） |
| **96 GB（98304）** | **127.11 GiB** | **跑通**：1 步 215.49 s / 端到端 488.72 s | **97.99（77.1%）** |

**判据（三条）：**

1. **主项是装载，不是分辨率。** 三档峰值提交：480p **88.67**、720p **88.32**、1080p **97.99** GiB。
   480p 与 720p 几乎一样 → 吃内存的是「int8 / nvfp4 权重在主机侧展开 + DiT 部分卸载」；
   1080p 多出来的约 10 GiB 才是 latent 与计算缓冲。
2. 🔴🔴 **64 GB 是最坏的一档，比 48 GB 更危险。** 48 GB 是干净崩（AV），64 GB 是**爬到 96.8% 停住不动**：
   离 100% 只剩 3 GiB，机器没崩只是运气。这与 17:00 那次整机卡死是同一形态
   （分配失败不报错 → 退化成重试 → 提交量顶穿）。**「能跑但没余量」比「跑不了」更危险。**
3. ✅ **定稿：`e://pagefile.sys` 初始 = 最大 = 98304 MB（96 GB 固定），提交上限 127.11 GiB，余量 23%。**
   只跑 ≤720p 的机器 64 GB 理论够（88.32 / 95.11 = 92.9%），但 7% 余量不算余量，**出视频一律 96 GB**。

**交付配置复测（单文件 96 GB 落 E:，重启后，B65 卡 0，6 步 / 5 秒）**：

| 分辨率 | 端到端（冷 / 热） | 单步（冷 / 热） | 峰值提交 |
| --- | --- | --- | ---: |
| 864×480 | 322.37 / 301.69 s | 11.03 / 10.69 s/it | 88.24 GiB |
| 1280×720 | 538.09 / 494.21 s | 42.69 / 42.48 s/it | 89.18 GiB |
| 1920×1088 | 1,429.91 s（只跑冷启） | 191.44 s/it | 95.61 GiB |

（中间那版「96 GB 分散在 E/F/D」的三文件拼法：480p 318.57 / 282.67、720p 518.21 / 485.54、1080p 只跑 1 步 488.72 s、峰值 88.67 / 88.32 / 97.99 GiB。
单步与交付配置一致，端到端差 ≤4%。）

⚠️ **端到端比 10-21 那批慢 23 至 42%，单步只差 0.4 至 3.6%** —— 差异全落在固定开销上，而且**跟分辨率无关**：
480p 164 → 256 s（+92）、720p 183 → 282 s（+99）、1080p 194 → 281 s（+87）。
⚡ **「布局不同」这个猜测已被第三个数据点否掉**：重启落成**单文件 96 GB 落 E:** 后再测，
480p 318.57 → **322.37 s**、720p 518.21 → **538.09 s** —— 几乎不动（+1.2% / +3.8%）。
→ **交付配置实测（单文件 96 GB / E:）**：480p **322.37 / 301.69 s**、720p **538.09 / 494.21 s**（冷 / 热），
单步 11.03 / 10.69、42.69 / 42.48；峰值提交 88.24 / 89.18 GiB。
成因仍未定位（候选：装载路径的某次额外初始化、页面文件被当作常驻后备时的读放大），**跨配置只比单步**。

## 6. 已落的护栏（代码）

`bench/harness/dual_ctx_probe.py` 改了三处，都是这次用命换来的：

1. **`--max-commit-frac`（默认 0.90）**：长请求发出前先读 `GlobalMemoryStatusEx`，
   提交量超过 commit limit 的 90% 就**不发**，直接记 `skipped_commit_ceiling`。
   宁可少拿一个数，不再赔一台机器。
2. **`--long-timeout` 默认 900 s**（原来 3600 s）：第一轮就是干等一小时，白赔时间。
3. **每个阶段落盘**：短请求一跑完就写 JSON，长请求哪怕把机器跑挂，已得的数字也在盘上。
4. 🔴 **`--job-commit-gib`（Job Object 内核硬限额）**：把 llama-server 关进 job，
   `ProcessMemoryLimit` 封顶进程 commit。超限的分配**直接失败、进程退出**，
   不存在 17:00 那条「分配失败不报错 → 退化成重试 → 顶穿整机」的路。
   自检：1.5 GiB 的 job 里 `bytearray(3 GiB)` → `MemoryError`，进程 rc=7，整机无感。
   ⚠️ 64 位下 `CreateJobObjectW` / `OpenProcess` 必须声明 `restype = HANDLE`，
   否则句柄按 `c_int` 截断、`AssignProcessToJobObject` 静默返回 False。
5. 🔴 **`_run_in_job.py --limit-gib N -- <命令>`**（工作区根目录，不进仓库）：把整条链路
   （`bench_f_h3.py` + 它拉起的服务子进程）关进一个 Job Object。子进程自动继承作业，
   所以只套最外层就够。自检：1.5 GiB 的作业里 `bytearray(3 GiB)` → `MemoryError`，整机无感。
   本次 1080p / 720p / 480p 全部按 `--limit-gib 100` 跑。
6. 🔴 **`_monitor_commit.py --frac 0.88 --kill bench_f_h3 --kill main.py`**：外部看门狗，
   每 2 s 采整机 Committed / Commit Limit，超线**自己动手杀进程**并落盘 `ABORT` 行。
   22:04 那次是它在 96.8% 把人叫停的（当时阈值 0.95、只报警不杀）；之后阈值降到 0.88 并接上自动刹车。
   ⚠️ **`--kill` 的子串必须带端口**（如 `--kill "listen 127.0.0.1 --port 8190"`）：
   只写 `main.py` 会连 8188 常驻实例一起杀 —— 那是用户日常用的那个，不许杀。
5. ⭐ **零 GPU 等效证明：`commit_ceiling_probe.py`**。只 `VirtualAlloc(MEM_COMMIT)` 不 touch
   （不计物理页、不写盘），每 GiB 一步，剩余可用 commit 低于 `--guard-gib` 就停手。
   用它回答「3M 会不会被拦」，完全不必拿 GPU 赌：
   48 GB 配置下实测最多提交 **55.00 GiB** 就触保护线，理论天花板 79.11 → 86.02 够不到。

## 7. 对外口径

- **3M 上下文只作「分配上限」记录**：起得来、短请求正常（decode 31.86 tok/s），
  但一条 35k token 的长 prompt 直接把机器跑死 → **不能当可用容量对客讲**。
- **可用上限仍按：单卡 1M token / 双卡默认 1.75M token。** 这两个数在 10-23 的容量记录里
  有显存按比例上涨的证据，是「真吃进显存」的上限。
- 对客一句话：**「买容量要看主机内存，不只是显存。」** 32 GB 内存的机器，双卡上下文的上限
  由 43.59 GiB 的 KV + 主机提交天花板共同决定，不是由 62 GB 显存决定。
