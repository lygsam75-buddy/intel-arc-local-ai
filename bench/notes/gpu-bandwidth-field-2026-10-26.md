# `zesMemoryGetBandwidth` 字段：单位错 + 会塌陷（2026-10-26 结案）

**一句话**：这个字段报的「带宽上限」既**不是 bytes/s**（偏大 4.8576%），**也不能当分母**
（解码期掉到 1/8，比实测流量还低）。占用率一律拿**规格值**算。

---

## 1. 是怎么踩进来的

| 时间 | 发生了什么 | 当时的结论 | 状态 |
|---|---|---|---|
| 10-26 16:25 | 第一次采解码带宽，采样窗口没对上负载，峰值只 39% | 以为采样太早 | 作废 |
| 10-26 17:17 | 采到满载，报出**占用 331.8%** | 以为分母是硬件的、流量算错了 | 作废 |
| 10-26 17:20 | 改成「每样本用自己的字段当分母」，重跑 | 还是 **336.2%**，50 个样本字段恒 79.7 | 作废 |
| 10-26 22:19 | 逐字段 dump + 两块卡比对 | **单位错**，且解码期塌到 1/8 | ✅ 结案 |

三次里前两次都是「换个算法再试一次」，没有去问「这个数是谁给的」。第三次改成
**把结构体整个 dump 出来看哪个字段在动**，十分钟就破了。

---

## 2. 决定性证据：单位不是 bytes/s

同一块卡读数 vs 规格：

| 卡 | 规格 | 规格 × 2^20/10^6 | 字段实测 | 反算 |
|---|---:|---:|---:|---:|
| B60 24G | 456 GB/s | **478,150,656,000** | **478,150,656,000** | 456.0 |
| B70 32G | 608 GB/s | **637,534,208,000** | 637.5e9 | 608.0 |

**逐字节相同**，不是「差不多」。两块不同规格的卡落在同一个常数比上，只可能是编码问题：

```
正确 bytes/s = 字段读数 ÷ 1.048576        （1.048576 = 2^20 / 10^6）
```

驱动把「456 GB/s」当成「456,000 MB/s」，再按 1 MB = 2^20 B 换算了一次。
→ **没有 4.8% 的超频余量**，那就是规格值本身。旧笔记里「256-bit × 19.9 Gbps ≈ 636.8，
理论上限比规格还高」的解释**作废**（那个数字碰巧接近，但不是它的来源）。

## 3. 字段布局：以行为为准，不以头文件为准

标准头文件写的是 6 个字段
（`readCounter / writeCounter / totalCounter / currentBandwidth / maxBandwidth / timestamp`，
即 offset 0 / 8 / 16 / 24 / 32 / 40）。**本机驱动不是这样填的**：

| offset | 实测行为 | 判定 |
|---:|---|---|
| 0 | 5.1e14 且持续增长，2 s 涨 198 GB | 读累计字节 |
| 8 | 1.2e14 且持续增长 | 写累计字节 |
| **16** | 恒 478,150,656,000（B60）/ 637.5e9（B70） | **带宽上限（带单位错）** |
| 24 | 每秒精确 +1,003,000 | **微秒时间戳** |
| 32 / 40 / 48 / 56 / 64 | 恒 0 | 驱动不填 |

所以「offset 16 = totalCounter」在这里不成立 —— 累计计数器不可能在读写各涨 198 GB / 164 GB
的同时自己纹丝不动。**按标准布局去读 maxBandwidth（offset 32）会拿到 0。**

## 4. 它还会塌陷

B70 跑 Vulkan 解码（`llama-bench -p 0 -n 1024 -r 6`，tg1024 = 121.72 tok/s）时：

- 50 个样本，字段**全部**报 79.7 GB/s；
- 79.7 ÷ 1.048576 = **76.0 = 608 / 8**，正好八分之一；
- 同期计数器差分实测 **280 GB/s**，是它的 **3.5 倍**。

**报出来的「上限」低于实测流量，物理上不可能** —— 这就足够判它不可用，不需要知道为什么。
（同为 B70，跑 H3 出视频时同一字段报满值，所以不是永久坏，是跟负载/状态有关。）

八分之一这个比例未解。**不影响上面的结论**，因为所有结论用的都是**计数器差分的绝对值**，
那个是实测流量，不依赖任何字段。

## 5. 现在的做法

`bench/harness/gpu_bandwidth.py` 已改：

1. 分母用 `--spec-bw`（224 / 456 / 608），**不用字段**；
2. 字段读数 ÷ 1.048576 后才记录，只作参考；
3. 任何样本的字段低于规格 50% → 打 `🔴` 并计入 `unreliable_samples`；
4. 实测峰值一旦超过字段最高值 → 直接打「字段不是上限，别当分母」。

```bash
python bench/harness/gpu_bandwidth.py -n 50 -i 1 --spec-bw 456 \
  --label b60-24g-decode-tg1024 --json bench/logs/bw_b60_decode.json
```

**B60 24G 补测（2026-10-27）**：Q4_0 全驻、`tg1024` 取满载 40 个样本 → **209.84 GB/s，占规格 456 的 46.02%**
（中位 210.12、最大 210.66；读 189.9 / 写 19.9）。它是同一次采样里最干净的一组，正好再验一遍分母规则：

| 分母取法 | 分母 | 占用率 |
|---|---:|---:|
| 规格值 | 456 GB/s | **46.02%** ← 对外只用这个 |
| 字段读数 | 478.15 GB/s | 43.88% |

两个值只差 2 个百分点，比 B70 那次（79.7 对 637.5，差 8 倍）温和得多 —— **正因为温和才更容易蒙混过关**：
这个差就是 2^20 与 10^6 的差（478,150,656,000 = 456 × 2^20/10^6），是单位错不是物理量。
🔴 顺手排掉一个旧数：本笔记早前记的「B60 191 GB/s / 42%」是把 llama-bench 收尾的 10 个衰减样本
（205.66 → 168.68）也算进均值的口径，**50 个全算 = 44.98%**。满载 40 个才是 46.02%。
`tg1024 = 97.16 ± 0.25 tok/s`；跨卡表用的是 `tg128 = 86.98`，**两者不可混比**。
数据件：`bench/data/2026-10-27_b60-24g-decode-bandwidth.json`。

## 7. 教训

1. **两次「换个算法再试」不如一次「把原始结构 dump 出来」**：字段到底哪个在动，看一眼就知道。
2. **出现 336% 这种数，先怀疑分母，不是怀疑分子** —— 物理量超标 3 倍，错的一定不是物理量。
3. **「差不多」不算证据，「逐字节相同」才算**：637.5 与 636.8 只差 0.1%，靠这个会得出
   「驱动报得比规格高，说明有余量」的假结论；478,150,656,000 与 456 × 2^20/10^6 完全相等，
   才锁死是单位问题。
4. 头文件和实现不一致时，**以行为为准**，并且要把这个不一致写下来。
