> **价格口径（三篇外部参考统一）**
>
> 下面这些价是**用来算性价比的指标基准，不是当天的下单价**。
> 显卡价格一路在涨，汇率、运费、税率、平台优惠、地区仓差天天都在动 —— 我们不可能逐日同步，
> 所以**统一锁定 2026-10 各卡电商挂牌价**，只用它算「每一元买多少显存、多少带宽」这类比值。

> 结论看倍数，别把某一格当成报价。**真要下单，价格必须现查**：同一张卡当天因为店铺券、满减、地区仓，

**为什么 5090 要上这张表**：客户不一定懂专业卡的型号体系，但一定认识 5090。
市面上的 **5090 涡轮版就是双槽涡轮卡**，跟左边三张同一个形态、同一个 32 GB —— 它够格站进这一排，
而且它一进来，「32 GB 显存到底该花多少钱」这个问题就从抽象变成了看得懂的一排数字。

**5090 全文统一按 ¥52,999 记**（2026-10 京东；实际成交已在 **¥53,000 以上**，差几百块不改变下面任何比值）。
2026-10-27 搜索里出现过 **¥40,899 的工包报价**，那是无发票、无正规保修的渠道货，**已不成立，不再使用** ——
一份文件里摆两个 5090 价，谁引用都会引错。

🔴 **5090 这一行有一条必须跟着说**：**575 W 是 B65 的 2.88 倍**。一张卡要 850 W 以上的电源，
机箱风道、电费、机房配电都要另算。**想上 5090 的人，先算电源，再算显存。**

四条读法：

1. **B65 与 4500 连功耗都一样是 200 W**，价格差 **3.1 倍**（¥9,999 对 ¥30,999），每 GB 显存 ¥312 对 ¥969。
2. **B70 是 B65 的 1.90 倍价**（¥594 对 ¥312 每 GB），多出来的是 **12 个核**（20 → 32），不是显存。
3. **5090 涡轮版每 GB 显存 ¥1,656，是 B65 的 5.3 倍；功耗 575 W，是 B65 的 2.88 倍。**
   它给的是 **1,792 GB/s** 的带宽和最成熟的 CUDA 生态，**不是更便宜的显存** —— 这两件事客户经常混。
4. 四张卡每 GB 显存从 **¥312 到 ¥1,656 差 5.3 倍** —— 这一档买的是「32 GB 装不装得下」和「生态」，
   不是「每 GB 便不便宜」。B65 的 ¥312 是这四张里的地板价。

## 四、唯一可用的解码实测对照（N 卡一路 + A 卡一路）

### 4.1 N 卡一路（对方）

来源：`ggml-org/llama.cpp` **#28196**  
<https://github.com/ggml-org/llama.cpp/issues/28196>

- GPU：**RTX 5090 32 GB GDDR7**，驱动 **616.56**，Windows 11 build 26220
- llama.cpp：**b10741**（`9d817213a`），官方 `llama-b10741-bin-win-cuda-13.3-x64.zip`
- 命令：`llama-bench -m <model> -ngl 99 -fa 1 -p 1024 -n 400`，5 reps

| model                       | test   |                  t/s |
| --------------------------- | ------ | -------------------: |
| qwen3moe 30B.A3B Q4_K_M（对照） | pp1024 | **4,081.20 ± 89.86** |
| qwen3moe 30B.A3B Q4_K_M（对照） | tg400  |    **134.18 ± 1.84** |
| qwen35 27B Q4_K_M（dense）    | pp1024 |     1,515.83 ± 47.03 |
| qwen35 27B Q4_K_M（dense）    | tg400  |         30.09 ± 0.44 |

同一份报告里作者自己算的 roofline：`1792 GB/s ÷ 16.8 GB ≈ 107 t/s`，实测 30.09 只有 28% ——  
**说明 5090 在 qwen35 这条路径上自己也没吃饱**，所以 134.18 不是 5090 的天花板。

### 4.2 我们（本机实测，两条后端）

来源：`bench/data/2026-10-21_b65-q4-0-base.json`（SYCL）· `bench/data/2026-10-21_b65-q4-0-vulkan.json`（Vulkan）

- GPU：Arc Pro B65 32G，可用 **31.16 GiB**，ECC **关**，驱动 **32.0.101.9150**
- llama.cpp：**b11753**（`d8d92973c`），`-ngl 999 -fa on -ctk q8_0 -ctv q8_0 -ncmoe 0 -p 512 -n 128 -r 3`
- 模型：`Qwen_Qwen3.6-35B-A3B-Q4_0` **19.41 GiB**（Vulkan 走 `-dev Vulkan1` 避开核显）

| 后端               |        pp512 |     tg128 |
| ---------------- | -----------: | --------: |
| SYCL `opencl:0`  |   **670.06** | **53.09** |
| Vulkan `Vulkan1` | **2,013.51** | **89.27** |

### 4.3 比值 —— 🔴 上一版只用了 SYCL 那列，结论是错的

```
解码（SYCL）    134.18 /   53.09 = 2.53×
解码（Vulkan）  134.18 /   89.27 = 1.50×
预填充（SYCL） 4,081.20 /  670.06 = 6.09×
预填充（Vulkan）4,081.20 / 2,013.51 = 2.03×
带宽           1,792 / 608       = 2.95×
```

1. **解码比（2.53）比带宽比（2.95）小** → SYCL 路径下 B65 的解码效率比「按带宽等比缩减」好约 17%。
2. 🔴 **「预填充差 6 倍」是后端问题，不是卡的问题**：换 Vulkan 后只有 **2.03×**，正好落在硬件算力比（约 2.1×）上。  
   同一张卡换后端 = 预填充 **3.00×**、解码 **1.68×**（`server-config.md` §8）。  
   → **对客口径：跑 llama.cpp 用 Vulkan。** 用 SYCL 会白丢 3 倍预填充。
3. 对 **4500** 没有实测，只能按带宽折算：`896 / 608 × 53.09 ≈ 78 tok/s`。**这是推算，不是实测，对外必须说出来。**

### 4.5 怎么读 R9700 这组

- **B65 Vulkan 89.27 落在 77 至 127 里面** → 对 R9700 是 **0.70 至 1.16×，中位 0.86×**。
- **B65 SYCL 53.09** → 0.42 至 0.69×。
- R9700 调到 147 至 156 之后是 B65 的 **1.65 至 1.75×**，代价是换 AMDVLK + 社区补丁 + 多 **100 W**。
- 🔴 **B65 这一侧量化更小**（Q4_0 19.41 GiB，对方 Q4_K_XL ≈21 至 22 GiB）→ 每 token 少读约 8% 字节，  
  **上面的比值对 B65 偏乐观**。要做成正式数字得同文件同 build 复测，**R9700 不在机，做不了。**

## 五、R9700 四条硬伤（客户一定会问，按顺序讲）

1. **ECC 只在 Linux** —— AMD 官方规格页原文 `支持显存 ECC：Yes (Linux Only)`。  
   → **Windows 工作站部署等于没有 ECC。**  
   反过来，RDNA4 **默认开 GECC**，第三方实测有效带宽只有 **576 GB/s**（正好 640×0.9），  
   关掉后 101 → 110 tok/s（**+9%**）；Linux 上关它要内核参数 `amdgpu.ras_enable=0`。  
   → **两面不可兼得：Windows 满带宽无 ECC / Linux 有 ECC 但吃掉 10%。**  
   ⚠️ Windows 侧有没有等价开关**没有可靠记录，本项目未实测，别替 AMD 打包票。**
2. **没有 FP4**（官方最低 INT4 / 766 TOPs）。我们的 H3 工作流靠 **nvfp4 14.61 GB** 文本编码器档  
   才在 32 GB 内存机上跑通（int8 档 25.28 GB 加载即崩）→ AMD 侧只能落回 int8/int4 软件路径，  
   **对应方案本项目未测，不给数字。**
3. **Windows 双卡没有 P2P** —— `ROCm/rocm-systems` **#13715**（2026-10-19 开）：  
   Win11 26H2 + 2×R9700 + 9950X3D + X870E，`hipDeviceCanAccessPeer = false`，  
   跨卡传输全部走主机内存 → **tensor 并行比单卡慢 2.15×**（824/14.90 对 840/32.14），  
   拆层 868/31.25 只与单卡持平。**Windows 上第二张卡只能加容量，加不了速度。**  
   Linux 有 P2P（社区报约 13 GiB/s 单向）才恢复正常。  
   → 对照我们：**Windows 双 B65 拆层 +12 至 19%、双卡并发 +6.0%、x4 槽解码只损 4.8%。**
4. **HIP 路径不稳 + 工具链陷阱** —— llama.cpp HIP 在 gfx1201 上加载 Q6_K（23.4 GiB）后挂在  
   `cli_context::init()`；Vulkan 要 `RADV_PERFTEST=coop_matrix` 才开矩阵单元；  
   `glslc` 版本不对能把性能砍到 1/5（shaderc 2023.8 **110 tok/s** vs v2026.2-dev **19 至 25 tok/s**）。  
   **同一张卡换编译器差 5 倍 —— 第三方数字为什么满天飞，这就是原因。**

⚠️ 附带一条相关的坑（**不当结论**）：上面第 4 条那位作者在 **32 GB 主机内存**的机器上跑 Q6_K，  
权重明明全在显存里，仍被 **global OOM 杀掉整个桌面**（Vulkan staging buffer + page cache + 桌面进程）。  
那是 Fedora + KDE + 三卡枚举的环境，和我们的 Windows 测试机不同；但与本项目「32 GB 内存是硬约束」的  
前提撞在一起，值得当成风险提示记下来。
