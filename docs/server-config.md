# server 交付配置：16 GB 档是三个错误叠在一起，24 GB 档只差「装得下」

> 这份文档的对象是**真实的交付配置**——客户装完、跑起来、看到的那套命令行，  
> 不是实验室里手搓的参数。  
>
> **16 GB 档（§1~§6）**：权重 19.41 GiB 装不进 15.51 GiB 显存，这条命令行实测 **5.76 tok/s**；  
> 把三个变量逐个拆开后修正为：**修好后 ×6.2 → 35.5~37.6 tok/s**。拆开的依据见 §5.1。  
>
> **24 GB 档（§7）**：同一条命令行只把 `-ncmoe` 由 8 改 0（权重装得下），
> **50.94 tok/s**，且 `-c` 从 16K 开到 256K 吞吐不变、视觉塔免费。见 §7。  
>
> **换后端（§8）**：命令一行不改，只把二进制换成 Vulkan 构建，同一张卡同一 build 上
> decode 从 **51.79 → 85.59 tok/s**。这是目前单项收益最大的一条。见 §8。

## 1. 交付配置：一条看起来很正常、实际是最差的命令行

```
llama-server.exe -m Qwen_Qwen3.6-35B-A3B-Q4_0.gguf \
  --host 127.0.0.1 --port 8080 \
  -ngl 999 --cache-type-k q8_0 --cache-type-v q8_0 \
  -c 262144 --parallel 1 --jinja \
  -lm dio --mmproj mmproj-Qwen3.6-35B-A3B-Q8_0.gguf \
  --image-min-tokens 1024 --api-key local
```

权重 **19.41 GiB → 装不进显存，也装不进内存**。

**同一套参数、两种机器状态下的实测吞吐（口径 B，`/completion`，prompt 13 token / 生成 104 token）**：

| 机器状态 | 槽位 | 空闲内存 | decode | prefill | 单请求墙钟 |
| --- | --- | ---: | ---: | ---: | ---: |
| 内存充足 | **主槽 PCIe 5.0 x8**（CPU 直连） | 20.9 GB | **5.76 tok/s** | — | — |
| 内存吃紧 | **副槽 PCIe 4.0 x4**（芯片组） | **5.2 GB** | **2.47 tok/s** | 7.97 tok/s | 43.36 s |

> 两行差 **2.3×**，而槽位与空闲内存**两个变量同时不同**，**无法归因到单一变量**。
> 下文所有倍数一律从「内存充足 · 主槽 x8」这一行的 **5.76** 起算。

> 关于第二行：`docs/slot-comparison.md` 测出「槽位不造成可测量损失」，
> 但那是**在 `-ncmoe ≥ 8`（专家已卸载）的前提下**测的。
> 本节的配置是 `-ncmoe` 缺省，走的是**整层 offload**，权重每个 token 都要过 PCIe ——
> 这种形态下 x8 与 x4 的差别**大概率不再可忽略**。两者不矛盾，是适用条件不同。

## 2. 为什么慢：三个叠在一起的错误

### 错误一：没加 `-ncmoe`（**但不是主因**——量级被高估了）

`-ngl 999` 的语义是「把能放的层尽量放显存」。**放不下时 llama.cpp 自己退化成  
整层 offload**——整层权重在 PCIe 上来回搬。实测这个模式下 **3.06 tok/s**（`-ncmoe 0`）。

`-ncmoe 8` 只把**专家**放 CPU，attention / router / 共享专家留在 GPU，  
通信量小一个量级。日志里看得见这一步：

```
-ncmoe 0：SYCL0 model buffer size = 18731.34 MiB   SYCL_Host =   272.81 MiB
-ncmoe 8：SYCL0 model buffer size = 15195.34 MiB   SYCL_Host =  3808.81 MiB
```

`-ncmoe 0` 时 **18731 MiB 全量往 15882 MiB 的卡上塞**，超出的 ~2.8 GiB 只能常驻主机内存、
每个 token 都被拉回来。`-ncmoe 8` 把 3808.81 MiB 显式放到 `SYCL_Host`（主机侧，**不是溢出**），
显存侧只剩 15195.34 MiB，装得下。

**这一项的单独贡献是 ×1.79**（5.76 → 10.30，同一会话内拆分，见 §5.1）——  
真正的大头是 `-c`。**三个改动不能混起来算，混起来会得到一个虚高的倍数。**

> `-ngl 999` 是「尽量全放」的意思，不是「保证全放」。  
> **在 16 GB 上它一定放不下，所以它一定是最差配置。**  
> 这个参数在 B70（32 GB）上凑巧能用，搬到 B50 就是坑。

### 错误二：`-c 262144`（256K 上下文）远超 16 GB 能力

262144 token 的 KV cache 在 16 GB 卡上不可能驻留。  
llama.cpp 按需分配，代价是**运行期持续走页面文件换页**——  
这正是内存吃紧那一档只剩 5.2 GB 空闲、server 进程 working set 高达 19.3 GB 的原因。

**但这里必须补一个前提，否则会把结论说错**：`-c 262144` **是为长上下文负载设的，不是随手填的**。
把它压到 16384，这类负载会被直接拒掉（HTTP 400）——**往下压不是解法，是把服务压坏**。

→ **所以这不是一个"参数调错了"的问题，是档位不匹配**：

| 事实                           | 含义                 |
| ---------------------------- | ------------------ |
| 客户侧的长上下文 agent 负载要 ~19 万 token  | 这是真实负载，不是压测        |
| 263K KV 在 16 GB 上不可能驻留       | 需求超出 B50 能力        |
| 压到 16384 → 请求被拒              | **往下压不是解法，是把服务压坏** |

**结论**：B50 16G 跑不了这个 agent 负载，  
**要满足 19 万 token 上下文得上升档位（B60 24G / B65·B70 32G）**，  
而不是"把 `-c` 调小"。16 GB 档能给的上下文天花板已实测，见 §5.2。

### 错误三：`--mmproj` 视觉塔与文本权重同驻（**但它不是"装不下"，是"白付钱"**）

先纠正一个直觉：视觉塔**并没有**把 16 GB 挤爆。实测它带来的增量只有
**独显 +204 MB、共享 +606 MB**，服务照常起、图像理解也真的跑通了（§5.4）。
所以这条不是"装不下"，而是：**纯文本推理白付一笔钱**（decode −11.5%、prefill −35%）。

**纯文本场景不该默认挂 mmproj**，需要多模态时再开。

## 3. 修法（按优先级，倍数已按同会话拆分）

| 优先级    | 改动                                            | 单独贡献（同会话实测）                                    |
| ------ | --------------------------------------------- | ---------------------------------------------- |
| **P0** | `-ngl 999` → `-ngl 999 -ncmoe 8`              | **×1.79**（5.76 → 10.30）                        |
| **P0** | `-c 262144` → **不是把数字调小就能解决**                 | **×3.05**（10.30 → 31.45）；但见错误二：压到 16384 会让长上下文负载被拒，这是档位问题不是参数问题 |
| **P1** | 纯文本场景去掉 `--mmproj`                            | **×1.13**（31.45 → 35.55）                       |
| P2     | 机器只有 32 GB 内存时，页面文件设 **64 GB 初始 / 128 GB 最大** | 唯一可扩展的「内存」，属硬性交付项                              |

> **三个改动合起来 ×6.2**（5.76 → 35.55），不是某个参数一个人的功劳。
> 各步的单独贡献见 §5.1 的同会话拆分表。

**32 GB 内存 + 16 GB 显存的客户机器上，正确配置长这样**：

```
llama-server.exe -m <model>.gguf \
  --host 0.0.0.0 --port 8080 \
  -ngl 999 -ncmoe 8 \
  --cache-type-k q8_0 --cache-type-v q8_0 \
  -c 16384 --parallel 1
```

> **`-c 16384` 这句要连同限制一起给客户**：`-c` 是**档位**不是旋钮。
> 16 GB 卡上它挡住的不只是「装不下」，还有 agent 负载本身（19 万 token 需求）。
> 客户如果要跑长上下文 agent，正确动作是**升级到 B60/B65/B70**，不是把 `-c` 改小。

## 4. 复现与验证方法

### 4.1 量之前先清场（不清就会量到别人的数）

本机装了一个保活脚本 `<部署目录>\watchdog.bat`：它每 15 秒探一次 `127.0.0.1:8080`，  
端口没人服务就把 `llama-server` 拉起来（机制与证据见 `docs/pitfalls.md` 3.4）。  
`Stop-Process` 硬杀会被它**15 秒后复活**——你以为在独占 GPU，其实全程有个 20 GB 的服务在抢显存。

**正确停机**：走部署自带的 `stop_model.ps1`（等价双击「停止本地模型.bat」）。  
它一次清掉三样：`llama-server.exe`、跑 watchdog 的 `cmd.exe`、`wscript`（`watchdog_silent.vbs`），  
并落下 `model_off.flag` 抑制每 2 小时的健康检查自动化。**该 flag 有 6 小时 TTL**，超时会失效。

清完先确认这三样都不在了，再开始采集。

**注意一个连带效应**：部署的「切到千问.bat」（`switch_to_qwen.ps1`）本身**会重新拉起 watchdog**——  
它先让 ComfyUI 走 `POST /free` 释放显存（不必杀 ComfyUI），  
再调 `<工具目录>\restart_model_clean.ps1 -Bat watchdog.bat`，由后者启动服务并校验权重确实落在 GPU 上。  
这是**有意设计**（保活 + 启动校验），但意味着：

> **每次开测前都要重新清一次场**，不能假设"上次清过就一直是干净的"。

反过来，如果这台机器不需要开机自启，可以把  
`%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\watchdog_silent.vbs` 移走  
（等价于跑 `uninstall_autostart.bat`）——只影响登录自启，**不影响手工开**。

### 4.2 量法

`bench/harness/probe_server.py` 量的是**运行中的 server 本身**，  
不需要停服务重建，也不需要猜参数——这正是对客口径该有的量法。
批量扫配置用 `bench/harness/ctx_sweep.py --api-key <key>`。

```bash
python bench/harness/probe_server.py --port 8080 --api-key local --n-predict 256
```

**鉴权（2026-10-16 逐个试过，别猜）**：server 带 `--api-key local` 时——
`Authorization: Bearer local` ✅ / `X-Api-Key: local` ✅ /
`bearer local`（**scheme 必须大写**）❌ / body 里放 `api_key` ❌ / 不带凭据 ❌，后三者都是 401。

> **这里踩过一次坑**：`--api-key local` 只写进了 server 侧的启动参数，
> 没同步给探针，于是 4 组配置**全部 401、速度字段全空**，
> 而加载日志、显存读数一切正常 —— **看起来像跑通了**。
> 扫配置时 `--api-key` 要同时给 server 和 client 两边。

脚本把 `Authorization: Bearer <key>` 放进请求头（llama-server 只认头），  
返回 `predicted_per_second` / `prompt_per_second` / `prompt_n` / `predicted_n` / `wall_s`。

**纪律**：任何对外报的速度，必须是**客户照着抄就能跑出来的配置**上量出来的，  
不是实验室 `llama-bench` 的峰值。它比任何 benchmark 都更接近客户的真实体验。

> **但「接近」不等于「可直接引用」**：这套量法量的是**某一个具体进程在某一个具体时刻**的表现，
> 而会话之间本身有约 **±5%** 的波动（§5.1）。
> 引用时用「约 37 tok/s」这种精度，不要引用小数点后一位。

## 5. 实测结果

**测试条件**：Intel Arc Pro B50 LP 16G（`DEV_E212` / `SUBSYS_25221EF7` 蓝戟）·
**主槽 PCIe 5.0 x8（CPU 直连）** · ECC off · 驱动 32.0.101.8976 ·
RAM 31.1 GiB + 页面文件 64 GB · llama.cpp build 11431 / `c25030496` · SYCL ·
模型 `Qwen_Qwen3.6-35B-A3B-Q4_0`（19.41 GiB）· 每组 1 次预热 + 4 次采样。

数据：`bench/data/2026-10-16_b50-16g-q4_0-*.json` /
日志：`bench/logs/2026-10-16_*.log`

### 5.1 按 §3 修正配置的数字：**≈37.5 tok/s**

按 §3 的修正配置（纯文本、无 `--mmproj`）：

```
-m <Q4_0> -ngl 999 -ncmoe 8 -lm dio --fit off --jinja --api-key local --parallel 1 \
  --cache-type-k q8_0 --cache-type-v q8_0 -c 16384
```

> 配置里带 `--fit off`：`--fit` 默认**开着**，会先跑一次试算加载，
> 把日志里的 `buffer size` 写成 0.00 的假数。要读真显存账就得显式关掉（见 `docs/pitfalls.md` 4.5）。

| 项 | 值 |
| --- | --- |
| **decode** | **37.45 / 37.55 tok/s**（两次独立会话，无 `-v`） |
| prefill | 46.52 / 48.60 tok/s |
| 加载 | 19.1 s / 16.5 s |
| 第三次会话（带 `-v` 逐 token 日志） | 35.55 tok/s（极差 3.5%） |

> **跨会话波动约 ±5%**：同配置、同参数、同卡，三个会话给出 35.55 / 37.45 / 37.55。
> 会话内极差只有 0.7~3.5%。所以**对外报「约 37 tok/s」，不要报小数点后一位**。

**三个改动各自的贡献（同一会话内拆分）**：

| 步骤 | 配置 | decode | 相对上一步 |
| --- | --- | ---: | ---: |
| 交付配置基线 | `c 262144` + `--mmproj` + `-ncmoe` 缺省 | **5.76** | — |
| ＋`-ncmoe 8` | `c 262144` + `--mmproj` | **10.30** | **×1.79** |
| ＋`-c` 压到 16384 | `c 16384` + `--mmproj` | **31.45** | **×3.05** |
| ＋去掉 `--mmproj` | `c 16384` | **35.55** | **×1.13** |
| | | | **合计 ×6.2** |

→ **`-c` 才是最大的一笔，`-ncmoe` 只占其中一小半。**

### 5.2 `-c` 的真实天花板：**32K 以内不溢出，64K 起开始掉**

Q4_0（19.41 GiB，必须卸载）+ `-ncmoe 8` + 纯文本，只改 `-c`：

| `-c` | KV buffer | 独显 MB | 共享 MB | **扣掉主机 buffer 后的真溢出** | decode | prefill |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 16384 | 170 MiB | 15,945 | 3,848 | **~39 MB** | 35.55 / 37.45 / 37.55 | 46.5 |
| 32768 | 340 MiB | 16,132 | 3,864 | **~55 MB** | **37.57** | 46.51 |
| 65536 | 680 MiB | 16,194 | 4,206 | **~397 MB** | **26.62（−29%）** | 26.84 |
| 262144 | 2,720 MiB | 16,030 | 7,160 | **~3,351 MB** | **10.35（−72%）** | 24.01 |

**结论**：

1. **拐点落在 32K 与 64K 之间。** 16K~32K 溢出量在 55 MB 以内（噪声级），速度满速；
   到 64K 溢出 0.4 GB，decode 直接 **−29%**；`-c 262144`（= 交付配置那条命令的值）
   溢出 3.35 GB，decode **−72%**。
2. **`-c` 是"花钱才有的"，不是"免费分配"。** 这与 `docs/vram-16gb.md` D.1 在
   **IQ2_M 全驻留**上测出的「跨 64 倍上下文只掉 1.6%」**不矛盾**：
   IQ2_M 有 4.78 GiB 显存余量，KV 涨 2.7 GiB 也吃得下；
   **Q4_0 靠卸载，上卡的部分已经贴到 15.9 GiB 的边**，KV 每涨一点就直接变成溢出。
   → **「`-c` 不花钱」是「装得下」时的结论，不能套到「装不下」的档位上。**
3. **还是那句：这不是把 `-c` 调小就解决的问题。** 16K~32K 满速只是个技术事实；
   客户真实的 agent 负载要 19 万 token，那个需求在 16 GB 档上**不存在可行解**。

> ⚠️ **读 `vram_shared_mb` 时会踩的坑**：
> `-ncmoe 8` 会把 3808.81 MiB 的专家权重**刻意**放进 `SYCL_Host`，
> 这部分**会计入 `vram_shared_mb`，但它不是溢出**。
> 上表「真溢出」一列是拿 `shared − 3808.81` 算的。
> 直接把 shared 当溢出读，会把 16K 档误判成"已经溢出 3.8 GB"。
> 详见 `docs/pitfalls.md`。

### 5.3 纯文本 vs 带 `--mmproj`：decode **−11.5%**，prefill **−35%**

同一会话、同 `-c 16384`、同 `-ncmoe 8`，唯一变量是 `--mmproj`：

| | 独显 MB | 共享 MB | decode | prefill |
| --- | ---: | ---: | ---: | ---: |
| 无 `--mmproj` | 15,944.6 | 3,848.1 | **35.55** | 42.93 |
| 带 `--mmproj` | 16,183.1 | 4,454.1 | **31.45** | **27.94** |
| 差 | +238.5 | +606.0 | **−11.5%** | **−34.9%** |

- **视觉塔常驻的增量（实测差值）：独显 +204 MB、共享 +606 MB。**
- 代价不只是显存：**prefill 掉 35%** —— 即使请求是纯文本，挂上 mmproj 之后
  prefill 也从 42.93 掉到 27.94。纯文本请求也要走一遍多出来的那部分计算图是**推测**，
  机制未查清，登记为 `[待解]`；但「挂了就掉」这个现象是实测的。
- → **纯文本场景不要默认挂 `--mmproj`**；要做多模态就单独起一个实例，或按需切换。

### 5.4 视觉塔 + 16 GB 主权重同时驻留：**能，且实测跑通了图像理解**

对客问题「**B50 能不能跑多模态**」的答案是 **能**，但要说清代价。

**驻留**：

| 项 | 值 |
| --- | --- |
| 日志证据 | `load_model: loaded multimodal model, 'mmproj-Qwen3.6-35B-A3B-Q8_0.gguf'` |
| 加载耗时 | 21.1 s |
| 独显 | 16,148.6 MB（纯文本同配置 15,944.6 → **视觉塔 +204 MB**） |
| 共享 | 4,434.1 MB |

**真的看见了**（不是"服务起来了"就算）：

送一张 640×360 的 PNG（白底，从左到右：红方块 / 绿圆 / 蓝方块），
问「列出图中形状及其颜色」。**正确答案唯一：3 个形状，红、绿、蓝。**

| 轮次 | 墙钟 | image prompt tokens | 回答 |
| ---: | ---: | ---: | --- |
| 第 1 次 | **102.9 s** | **1113** | `red square, green circle, blue square` ✅ |
| 第 2 次 | **0.44 s** | 4（缓存命中 1109/1113） | 同上 ✅ |
| 第 3 次 | 0.44 s | 4（同上） | 同上 ✅ |

- **图像被编码成 1113 个 prompt token**（`--image-min-tokens 1024` 生效），
  **首张图要等 ~103 s** —— 这段是图像 prefill，速率只有 **10.8 tok/s**。
- **同一张图再问是免费的**（0.44 s）：llama-server 的 prompt cache 会把图像 token 也缓存住。
- 生成侧 decode **30.52 tok/s**，与纯文本同量级。

**→ 对客话术**：

> 「B50 16G 能跑多模态。多模态的代价不在显存（视觉塔带来的增量是独显 +0.2 GB、
> 共享 +0.6 GB），在**首张图的等待**——每张新图要过一遍视觉塔，约 100 秒
> （图像被编码成 1024~1113 个 token，图像 prefill 只有 10.8 tok/s）。
> 同一张图再追问是即时的（0.44 s）。要连续处理大量不同图片，那才需要上更高的档位。」

**⚠️ 判定时踩的坑（差点误判成"跑不起来"）**：

第一次跑用 `max_tokens: 96`，返回 `completion_tokens: 96` 但 **`content` 是空字符串** ——
96 个 token 全被推理模型的思考阶段吃掉，还没轮到正文就撞上限。
**看起来完全像"多模态跑不起来"**：服务正常、速度有值、没有任何报错。

正确做法：给足预算（512），或直接 `chat_template_kwargs: {"enable_thinking": false}`。
关掉思考后**只用 9 个 token 就答对了**。
→ 已验证：`bench/harness/vision_probe.py`（送图 + 唯一答案核对 + 显存快照）。

## 7. 24 GB 档（B60）：同一条命令行只改一个参数，吞吐 1.4×，`-c` 到 256K 不花钱

B60 24G 可见 **23.33 GiB**，Q4_0 权重 **19.41 GiB** 装得下 —— `-ncmoe` 从 8 改 **0**，
其余与 §3 的 16 GB 交付配置逐字相同：

```
llama-server.exe -m Qwen_Qwen3.6-35B-A3B-Q4_0.gguf \
  --host 127.0.0.1 --port 8080 \
  -ngl 999 -ncmoe 0 \
  -fa on --cache-type-k q8_0 --cache-type-v q8_0 \
  -c 16384 --parallel 1 --jinja \
  -lm dio --api-key local
```

**测试条件**：Intel Arc Pro B60 24G（`DEV_E211` / `SUBSYS_25421EF7` 蓝戟）·
**CPU 直连槽** · ECC off · 驱动 32.0.101.9150 · RAM 31.1 GiB + 页面文件 64/128 GB ·
llama.cpp build 11431 / `c25030496` · SYCL · 每组 1 次预热 + **4 次采样**（`n_predict 128`）。

> 测得数在 `--fit off` 下采：`--fit` 默认开着会先跑一次试算加载，把日志里的
> `buffer size` 写成 0.00 的假数（`docs/pitfalls.md` 4.5），要读真显存账就得关掉。
> 客户配置里不需要这一句。
>
> `-c 16384` 是为了与 §3 的 16 GB 档逐字可比。**B60 上这一项可以自由加到 262144**
> —— §7.1 实测吞吐不变，代价只有显存。

### 7.1 `-c` 从 16K 到 256K：吞吐不变，显存涨 3.3 GB

| `-c` | KV buffer | 模型（真显存） | compute | **独显 MB** | 共享 MB | **decode** | 极差 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 16384 | 170 MiB | 18,731 MiB | 104 MiB | 19,235 | 326 | **50.94** | 2.1% |
| 32768 | 340 MiB | 18,731 MiB | 152 MiB | 19,453 | 342 | 50.73 | 5.4% |
| 65536 | 680 MiB | 18,731 MiB | 248 MiB | 19,889 | 374 | **51.54** | 0.3% |
| 131072 | 1,360 MiB | 18,731 MiB | 440 MiB | 20,761 | 438 | 50.94 | 2.8% |
| 262144 | 2,720 MiB | 18,731 MiB | 824 MiB | 22,506 | 566 | 51.35 | 2.1% |

（prefill 47.8~54.7 tok/s，加载 14.5~19.1 s）

> **结论：B60 上 `-c` 是纯容量旋钮，不是性能旋钮。**
> 16K → 256K 十六倍，decode 全距 **50.73~51.54（1.6%）**，落在会话内极差之内。
> 代价只有显存：19,235 → 22,506 MB（+3.3 GB），共享始终 326~566 MB —— **没跨过溢出线**。

这条与 §5.2 的 16 GB 档形成对照组，同一个量在两个档位上给出相反的结论：

| `-c` | 16 GB 档 decode（`-ncmoe 8`） | 24 GB 档 decode（`-ncmoe 0`） |
| ---: | ---: | ---: |
| 16384 | 35.55 | 50.94 |
| 32768 | **37.57** | 50.73 |
| 65536 | **26.62** | **51.54** |
| 262144 | **10.35** | **51.35** |

16 GB 档从 64K 起塌（−29% → −71%），因为共享溢出跟着从 3,848 涨到 4,206 / 7,160 MB；
24 GB 档到 256K 共享也只有 566 MB。**决定速度的是溢出量，不是 `-c` 这个数字。**

### 7.2 视觉塔：24 GB 档上不花钱，首图等待 103 s → 17 s（均为冷态）

同一条命令行加 `--mmproj …Q8_0.gguf --image-min-tokens 1024`：

| 档位 | decode | 独显 MB | 共享 MB |
| --- | ---: | ---: | ---: |
| 纯文本 · c16384 | 50.94 | 19,235 | 326 |
| **带视觉 · c16384** | **51.24** | 20,151 | 332 |
| 纯文本 · c16384（16 GB 档对照，`-ncmoe 8`） | 35.55 | 15,945 | 3,848 |
| 带视觉 · c16384（16 GB 档对照，`-ncmoe 8`） | **31.45** | 16,183 | 4,454 |

→ **24 GB 档 +0.6%（在 2.1% 极差内，等于免费）**，显存只多吃 917 MB，共享只多 6 MB。
→ 16 GB 档 **−11.5%**，因为视觉塔把 606 MB 又挤到主机侧（3,848 → 4,454）。

**但「装得下」还要「真的看见了」才算跑通。** 送一张答案唯一的图
（白底 + 红方块 / 绿圆 / 蓝方块），核对回答内容 —— 视觉塔没解码成功时，
模型会返回一段流畅但纯属编造的描述，tok/s 也照样有值：

| | B50 16G（`-ncmoe 8`） | **B60 24G（`-ncmoe 0`）** |
| --- | ---: | ---: |
| 显存 / 共享溢出 | 16,149 MB / **4,434 MB** | 20,097 MB / **332 MB** |
| **首张图墙钟** | **102.93 s** | **17.28 s**（5.96×） |
| 图像 prefill（1113 个图像 token） | **10.85 tok/s** | **65.21 tok/s**（6.0×） |
| decode（3 次） | 29.72 / 31.08 / 30.76 → **30.52** | 48.09 / 50.77 / 51.14 → **50.0** |
| 同图追问复用 | 0.44 s | **0.24 s** |
| 回答 | `red square, green circle, blue square` ✅ | `red square, green circle, blue square` ✅ |

**首图那 103 → 17 秒是这一节最值钱的数字**：图像 token 是**预填充**相位，
16 GB 档上视觉塔与专家都在主机侧，每个图像 token 都要跨 PCIe 回读权重；
24 GB 档全在显存里。推理模型的思考阶段会吃 token，测的时候要关掉
（`chat_template_kwargs: {"enable_thinking": false}`），否则 `content` 会是空串
—— 那看起来像「多模态跑不起来」（`docs/pitfalls.md`）。

> ⚠️ **表里两个首图数都是「冷态」（该后端在本机的首次跑），所以这一列可以直接比。**
> 同一个后端连跑第二次，首图会明显变快：B60 上是 **17.28 s → 7.0 s**（见 §8.3 的冷/暖两态表）。
> B50 的暖态**没有数据**（卡已拆下），所以「B60 暖态 7 s」不能拿去和「B50 冷态 103 s」比 ——
> 那样会把一次性代价算成卡的差距。跨卡只比同一态。
>
> 数据：`bench/data/2026-10-20_b60-24g-q4_0-vision-cold.json`（冷态，本节用这条）·
> `2026-10-20_b60-24g-q4_0-vision-nothink.json` / `2026-10-20_b60sy-vision-warm2.json`（暖态 ×2）·
> 日志：`bench/logs/2026-10-20_b60-24g-q4_0-vision-nothink.log`

**对客话术**：

> 「B60 上视觉塔不用单开一套配置 —— 装得下，它就只是多吃 0.9 GB 显存，速度不变。
> **装完第一次跑一张新图约 17 秒，之后每张新图 7 秒左右，同一张图追问是即时的（0.2 秒）**。
> B50 上同一件事第一次要等 103 秒，所以那边建议做纯文本/多模态两套配置，B60 不需要。」

### 7.3 `-ncmoe`：24 GB 档上卸专家是纯亏

同一条命令行只把 `-ncmoe` 由 0 改 8：

| 配置 | 模型（真显存） | 模型（主机侧） | 独显 MB | **共享溢出** | decode |
| --- | ---: | ---: | ---: | ---: | ---: |
| `-ncmoe 0` 全驻留 | 18,731 MiB | 273 MiB | 19,235 | **326 MB** | **50.94** |
| `-ncmoe 8` 卸 8 层专家 | 15,195 MiB | 3,809 MiB | 15,990 | **3,862 MB** | **45.89**（−9.9%） |

llama-bench 口径（`docs/vram-16gb.md` B 节）同方向：52.43 → 44.40（−15%）。
`-ncmoe` 只有在**装不下的时候**才是正收益（16 GB 档 ×1.79），装得下时纯亏。

### 7.4 跨卡：B50 → B60 的 1.4× 来自「装得下」，不是算力

同一套 harness、**同一个 llama.cpp build 11431**、同模型、同 prompt、`n_predict 128`、4 次采样：

| 卡 | 可见显存 | 交付配置 | 模型驻留 | 共享溢出 | **decode** |
| --- | ---: | --- | --- | ---: | ---: |
| B50 16G | 15.51 GiB | `-ncmoe 8` | 部分 | 3,848 MB | 35.55 / 37.45 / 37.55 |
| **B60 24G** | **23.33 GiB** | **`-ncmoe 0`** | **全驻留** | **326 MB** | **50.94** |

→ **1.36~1.43×**。显存带宽只差 2.04×（456 / 224 GB/s），速度却没那么大差距，
因为 B50 那 3,848 MB 溢出让每个 token 都要跨 PCIe 回读专家权重 —— 带宽优势被吃掉了。

> ⚠️ **B70 不在表里，也不能并排**：库里现有 B70 口径 B 只有 2 个样本，条件是
> `-c 8192` / `n_predict 512` / prompt 48 token / 驱动 8976 / 样本极差 13%，
> 与本表（`-c 16384` / `n_predict 128` / prompt 缓存命中 / 驱动 9150 / 4 样本）**不是同一条件**。
> 要并排得在 9150 上按本表参数给 B70 补一次。

## 8. 后端：命令一行不改，Vulkan 比 SYCL 快 1.65×

前面七节全在 SYCL 后端上做。**换后端不是调参，是换一个后端实现**：同一条交付命令行、
同一张卡、同一个 llama.cpp build，只把 `llama-server.exe` 换成 Vulkan 构建：

| | SYCL | Vulkan | |
| --- | ---: | ---: | --- |
| 交付配置 decode | **51.79** | **85.59** | **1.65×** |

这是目前所有单变量改动里收益最大的一条，也比 `-ncmoe`、`-c`、视觉塔三项加起来大得多。

### 8.1 为什么两边必须是同一个 build

llama.cpp 每个 nightly 都在改内核，跨 build 比后端会把**版本差**算进**后端差**里。所以这一轮
两边都用 **b11753（commit `d8d92973c`）**的官方预编译包，唯一的差别就是 zip 不同。

`llama-bench` 口径（`-p 512 -n 128 -r 3`，`-ngl 999 -fa on -ctk q8_0 -ctv q8_0 -ncmoe 0`）：

| 后端 | 设备钉法 | prompt tok/s | decode tok/s |
| --- | --- | ---: | ---: |
| **Vulkan**（build 11753） | `-dev Vulkan1` | **1934.28 / 1923.88** | **86.42 / 86.98** |
| SYCL（build 11753） | `ONEAPI_DEVICE_SELECTOR=opencl:0` | 670.47 | 52.25 |
| SYCL（build 11753） | `ONEAPI_DEVICE_SELECTOR=level_zero:0` | 648.55 | 50.69 |
| *SYCL（build 11431，参考）* | *`opencl:0`* | *961.22* | *52.43* |

→ decode **1.68×**、prefill **2.93×**（两列都按两次 Vulkan 的均值比 SYCL 两个运行时的均值）。

表里 SYCL 的三行是特意留的：**11431 与 11753 的 decode 只差 2%**（52.43 / 52.25），
所以下面 §8.2 拿 11753 的 Vulkan 去比 11431 的 SYCL 也站得住 —— 版本不是变量。

> ⚠️ 同一个 SYCL 构建下 `opencl:0` 与 `level_zero:0` 是两个不同的运行时，
> 两者都跑得通、**差 3%**（opencl 略快）。所以「SYCL 只认 opencl」这个说法不成立；
> 顺带把 `pitfalls.md` 待解 #5 里「可能一直在跑 OpenCL」这条做成显式对照：
> 是，两种都能跑，选哪个差 3%，不改变结论。

### 8.2 真 server 口径：交付配置 85.59

`llama-bench` 是峰值口径，对客报的必须是交付命令行上量出来的数（纪律见 §4.2）。
同一条命令行（`-fa on -ctk q8_0 -ctv q8_0 -lm dio --fit off --jinja --parallel 1`）、
`-ncmoe 0`、`n_predict 128`、4 次采样：

| 后端 | `-c` | decode | 独显 MB | 共享溢出 |
| --- | ---: | ---: | ---: | ---: |
| **Vulkan** | 16384 | **85.59**（84.34~86.15） | 19,144 | **4.9 MB** |
| Vulkan | 65536 | 85.19（82.27~86.27） | 19,703 | 4.9 MB |
| Vulkan + `--mmproj` | 16384 | 84.90（83.93~85.89） | 19,979 | 4.9 MB |
| SYCL | 16384 | 51.79（50.57~52.62） | 19,306 | 390 MB |
| SYCL | 65536 | 52.24（51.31~52.59） | 19,961 | 438 MB |

三件事同时成立：

1. **1.65×（16K）/ 1.63×（64K）** —— 与 `llama-bench` 的 1.68× 一致，说明差距不在「bench 与 server 的差别」上。
2. **`-c` 在 Vulkan 上依旧不花钱**（85.59 → 85.19，−0.5%，在采样极差之内），代价只有显存 +559 MB。
3. **视觉塔在 Vulkan 上也不花钱**（85.59 → 84.90，−0.8%），代价显存 +835 MB。

### 8.3 多模态：首图比 SYCL 快 1.45~1.52 倍

挂上视觉塔不等于「看得见」（`pitfalls.md` 记过：视觉塔没解码成功时模型照样会返回流畅但编造的描述）。
所以这一档是真的送图、真的核对答案。测试图 640×360，期望答案是画面里有红/绿/蓝三色，**四次全中**。

⚠️ **首图必须分「冷 / 暖」两态**：同一个后端在本机连跑两次，首图墙钟差到 **2.4 倍**
（SYCL 17.28 → 7.0 s，Vulkan 11.34 → 4.8 s）。这个一次性代价的机制**没有查明**
（日志里没有任何 JIT / 编译 / 缓存行，两边都不打），所以下面两种状态都列，不挑一个报。

| | SYCL 冷 | SYCL 暖 | Vulkan 冷 | Vulkan 暖 | 暖态比值 |
| --- | ---: | ---: | ---: | ---: | --- |
| **首图墙钟** | 17.28 s | **7.0 / 7.1 s** | 11.34 s | **4.8 / 4.9 s** | **1.45×** |
| **图像 prefill**（1113 token） | 65.21 | **164.3 / 161.8** | 99.29 | **237.9 / 234.8** | **1.45×** |
| decode（首轮） | 48.09 | 47.8 / 47.5 | 78.01 | 76.7 / 70.0 | — |
| decode（同图追问） | 50.77 / 51.14 | — | 80.59 / 80.59 | — | 1.58× |
| 加载 | 19.1 s | 19.1 / 20.1 s | 15.1 s | 14.6 / 16.6 s | — |
| 显存 / 共享溢出 | 20,097 / 332 MB | 20,017 / 334 MB | 19,978 / 2.6 MB | 19,978 / 2.6 MB | — |
| 答案核对 | PASS | PASS | PASS | PASS | — |

冷态与暖态的**比值几乎一样（1.52× / 1.45×）**，说明这个一次性代价与后端无关，
不影响 §8.1~§8.2 的结论。但**报绝对秒数时必须说是哪一态** —— 只报 17.3 s 会让人以为 Vulkan 也慢，
只报 4.8 s 会让人以为装完就能这么快。

图像 token 走的是**预填充相位**，所以首图等待的差距与图像 prefill 的差距逐位吻合（都是 1.45×）；
decode 那 1.58× 是另一回事（解码受限维度不同，见 §8.4）。

### 8.4 差距落在哪里：不是显存，是 kernel 效率

这一节是**排除**，不是归因。库里 §7.3 的结论是「B60 上唯一的归因轴是共享显存溢出量」，
很容易顺手把它套到这里 —— 套不上：

| 观察 | 数值 |
| --- | --- |
| B60 `-ncmoe 8`：溢出 3,862 MB | decode **−9.9%** |
| SYCL 后端：溢出 390 MB | decode **−40%** |
| Vulkan 后端：溢出 4.9 MB | decode 基准 |

**溢出量大 10 倍的那次只掉 9.9%，溢出量小 80 倍的那次掉了 40%** —— 溢出量不是这次的解释变量。
再加上**预填充也差 2.93×**：预填充是算力受限（512 token 一次性算完，几乎不吃带宽），
如果是显存/带宽问题，预填充不该掉这么多。两个维度同时差 → 指向**后端内核效率**。

Vulkan 后端在 Arc B60 上枚举出的能力（`--list-devices` 原文）：

```
matrix cores: KHR_coopmat
```

SYCL 侧对应的能力本机没有取证，所以「差距是否来自 coopmat」**未验证，不作结论**。
可以确定的是：这不是某个参数调错了，调参调不出来。

### 8.5 代价与限制（选后端前必读）

| 项 | 事实 | 影响 |
| --- | --- | --- |
| **设备枚举** | Vulkan 下第 0 张卡是**核显**（AMD Radeon Graphics，`uma: 1`，报 16,185 MiB 假容量） | 必须 `-dev Vulkan1` 钉卡。**不钉就落到核显上，日志照样像在跑** |
| **bf16 / fp4** | Vulkan 报 `bf16: 0`、`fp4: 0`；fp16 支持 | 本轮是 Q4_0 权重，不受影响；**bf16 权重模型在 Vulkan 上要单独验**，别直接沿用 |
| **覆盖范围** | 只测了 B60 24G × Qwen3.6-35B-A3B Q4_0，一个模型一个量化档 | B50 / B65 / B70 未测；其他量化档未测 |
| **`-c` / 视觉塔** | 与 SYCL 同向：都不花钱 | 无额外代价 |

### 8.6 装法

用官方预编译包，不需要 Vulkan SDK（系统里的 `vulkan-1.dll` 由显卡驱动自带，本机驱动 9150 已支持到 Vulkan 1.4.359）：

```bash
# 从 llama.cpp 的 nightly release 取 Windows x64 的 Vulkan 包，解压到独立目录
# 注意：不要和 SYCL 包混在同一个目录，两边的 DLL 名字有重叠
cd <解压目录>
./llama-bench.exe --list-devices     # 先看清 Vulkan1 是不是 Arc，再跑
```

⚠️ **必须在解压目录里执行**：这些 build 的 `*-impl.dll` 靠当前目录解析，
在别的目录直接调 exe 会报 `error while loading shared libraries`（退出码 127）。
