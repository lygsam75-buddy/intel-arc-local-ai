## 0. 编号与状态规则

| 前缀 | 含义 |
|---|---|
| `T-xx` | 测试项（一个要回答的问题） |
| `H-xx` | 采集工具（`bench/harness/` 下的脚本） |
| `D-xx` | 数据文件批次（`bench/data/*.json` 按 schema 分） |

| 状态 | 含义 |
|---|---|
| ⛔ 未测 | 没跑过 |
| 🔵 进行中 | 已开跑未出结论 |
| ✅ 已完成 | **四要素齐全**：口径定义、数据 JSON、文档结论、复现命令 |
| 🟡 初测 | 跑了但样本不足或只跑了部分卡，只登记不进基准表 |
| ↩️ 已撤回 | 出过数字后被证明无效，留档当反面教材 |
| ⏸️ 阻塞 | 有前置条件没满足（硬件没到、环境没搭） |

**编号永久复用、永不重排**。某项撤回或换方法，编号留着，状态改，原因写进备注。

**每次采集完跑一遍审计**（数量、schema、tool 覆盖率，30 秒）：

```bash
python bench/harness/registry_audit.py
```

### 命名规范与作废规则

```
bench/data/<日期>_<卡><显存>_<模型>-<量化>-<后端>.json
例：2026-10-15_b70-32g_qwen3.6-35b-a3b-q4_0-sycl-r3.json
```

- 换后端 = 新记录，不覆盖；作废记录**不删**，`status: discarded` + 原因 + `superseded_by`。
- 环境必填：`ram_gb` / `pagefile_gb` / `ecc` / `slot` / `tool` / `device_selector`，
  以及 **AIB 身份 `chip` / `subsys` / `device_id` / `board_vendor`**（Intel 同型号不同板厂未必同性能）。
  缺字段 = 不可比，`registry_audit.py` 会暴露。
- `env.env_confidence` 逐项标 `recorded` / `inferred`（**位置在 `env` 内**，2026-10-16 统一）。

### 功耗字段（2026-10-19 起，H-25）

`summary.power` 与 `samples[].power`。**`null` = 未采集，不是 0 W** ——
采集能力上线前的批次必然是 `null`，功耗无法事后补。

| 字段 | 含义 | 什么时候看它 |
|---|---|---|
| `card_domain` / `card_limit_mw` | 整卡电源域下标与其功率上限（B70 = `1` / `290000 mW`） | 确认「量的是整卡不是某个分区」 |
| `avg_w` / `energy_j` | **整轮**平均功率与总能量，**含模型装载、卸载、VAE 解码** | 算电费、算「一条任务多少焦耳」 |
| `p90_w` | 90% 的 1 s 窗口都不超过的功率 | **判断「有没有把卡压满」看它，不看 `avg_w`** |
| `peak_w` | 1 s 窗口峰值（**不是**示波器瞬时峰） | 电源与散热瞬态余量 |
| `busy_share` | 整轮里 1 s 窗口 ≥ 80% 功率上限的比例 | 装载主导的档位靠它才说得清「卡到底干了多少活」 |
| `counter_resets` | 整卡域能耗计数器的**归零次数**（计数器会中途重置） | `>0` 说明该窗口经历过重置。功率由**逐拍增量积分**算出、不受影响，但要能看见它才知道这段可不可信。**取不到是 `null`，不是 0** |

> ⚠️ **`avg_w` 会被装载段稀释**：864×480 的 cold 轮 `avg_w` = 135.0 W、`p90_w` = **290.1 W**，
> 因为 182.6 s 里只有 28% 的 1 s 窗口处在满载（其余在装载 / 解码）。
> 拿 `avg_w` 当「满载功耗」讲会**低估一半以上**。
> 反过来也一样：Krea-2 bf16 每轮重装，`avg_w` = 82.4 W、`p90_w` = **93.1 W** ——
> 这时**连 P90 都低**，说明这配置**根本没把卡压起来**（装不下）。
