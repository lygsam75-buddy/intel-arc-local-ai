## 〇、先读这一节：同一张卡、同一套 ComfyUI，int8 快慢取决于**内核变体**

**这是整份文档最重要的一张表。** 同一张 B70、同一套 ComfyUI 0.39、
同一份 `omni_int8fix.py` 补丁，唯一变量是 `omni_xpu_kernel` 的变体：

| Qwen-Image 2.1<br>1280×720 · 25 步 | 档 | `torch213.bmg`<br>（无 int8fix） | `torch212.bmg`<br>（有 int8fix） | 变化 |
|---|---|---:|---:|---:|
| **同提示词（稳态）** | `bf16` | 13.69 / 13.77 s | 13.79 / 13.85 s | **分毫未动** |
| 同提示词（稳态） | **`int8`** | 18.87 / 18.83 s | **10.63 / 10.63 s** | **快 1.78×** |
| 首次装载 | `bf16` | 96.66 s | 46.42 s | — |
| 首次装载 | `int8` | 28.04 s | 19.45 s | — |
| 换提示词 | `int8` | 19.27 s | **11.00 s** | **快 1.75×** |

**两条结论，方向完全相反：**

| 内核 + 栈 | int8 稳态 | bf16 稳态 | **int8 相对 bf16** |
|---|---:|---:|---:|
| `torch213.bmg` · 无 int8fix | 18.85 s | 13.73 s | **慢 37%** |
| `torch212.bmg` · 有 int8fix | **10.63 s** | 13.82 s | **快 23%** |

> **`torch213.bmg` 的 int8 GEMM 慢近一倍**——所以在它上面量到的
> 「int8 比 bf16 慢」**不是 Intel 卡的性质，是内核配错**。
> 换成 `torch212.bmg` 后，10.60 s **正中 gerrywang 声称的 10.3–10.6 s**。

### §0.1 两个「内核变体」到底是什么：不是新版 vs 旧版，是**同一版本的两个构建**

用户直觉「越高版本越好」在这里**方向对、对象错**。实测两个环境的构建：

| | `python_embeded` | `python_embeded_torch213` |
|---|---|---|
| torch | 2.12.0+xpu | **2.13.0+xpu** |
| `omni_xpu_kernel` 版本 | `0.2.0b2+torch212.bmg` | `0.2.0b2+torch213.bmg` |
| **kernel 的 `Requires-Dist`** | **`torch==2.12.0`** | **`torch==2.13.0`** |
| **配套 provider** | **0.2.33**（revision `950214ad`） | **0.2.31**（revision `9eccb7f`） |
| provider 声明的 torch | 2.12.0+xpu ✓ 匹配 | 2.13.0+xpu ✓ 匹配 |
| kernel 包体积 / 文件数 | 93.0 MB / 17 | 85.2 MB / 14 |

**两条必须记住的事实：**

1. **两个 kernel 的版本号完全相同（都是 `0.2.0b2`）**——
   上游 `VERSIONING.md` 明写：*「版本号由仓库所有者控制，**不得因为加了功能、修复、
   性能里程碑或依赖固定而改版本**」*。
   → **「版本号相同」不代表「功能相同」。**
2. **真正的版本序在 provider 上**：`0.2.33`（rev `950214ad`）**新于** `0.2.31`（rev `9eccb7f`）。
   **torch 2.13 并不是「更高版本的内核」，它只是更旧那套 provider 配套的构建。**

**torch 与 kernel 与 provider 是绑死的**（kernel 的 `Requires-Dist` 锁死 torch 版本、
provider.json 只声明单一 `torch_version`），**无法单独换其中之一**——
所以任何「换内核」的实验，测的其实是**整套**。

### §0.2 两套的差异到底在哪：不是「能力有没有」，是「实现成熟度」

| 对比项 | 结果 |
|---|---|
| kernel 独有文件 | torch212 那套**多 16 个真实文件**：`_compile_meta.py` / `_compile_ops.py`、`cute/sol_attn_v2.py` + 6 个 `sol_attn_*.hpp`、`policies/kernel-policy-v1.json`、`csrc/kernel_tuning_overrides.h` + `csrc/generated/*` |
| 核心扩展体积 | `cute/cute_fmha_torch.pyd`：**8.74 MB vs 1.50 MB（5.8 倍）**；`_C.pyd`：9.56 MB vs 8.41 MB |
| **注册的能力清单** | **实测两边完全相同**（都含 `int8_linear` / `mm_int8` / `quantize_int8_tensorwise` / `convrot_w4a4_linear` / `dequantize_int8_convrot_weight` / `prepare_int4_weight_for_int8_linear`） |

⚠️ **能力清单相同，不代表跑得一样快。** 上游 README 明确：
*「XPU 后端从**已安装的 companion wheel 里的 native 符号**独立注册每个能力」*、
*「一个 ✓ 仍可能有 dtype / shape / layout / **数值**限制」*。

→ **能力清单不能当性能依据**。10-15 那次测出 `torch213` 的 int8 GEMM 慢近一倍，
而两边能力清单一模一样 —— 这只可能是**同一能力背后的实现成熟度不同**。

> 📌 **两个「清单」要分清**：
> `Found comfy_kitchen backend xpu: {...'capabilities': [...]}` 是 **comfy_kitchen registry 层**
> 的能力表；kernel 包里 pyd 导出的 native 符号是**更下一层**。10-15 说的「符号更多」指后者。

### §0.4 实验设计：三个数据点才能拆开「torch / kernel / provider」

A 与 B 只对比「整套」，跑出来的差异**不能归给任何一项**。
10-15 那次「换内核 int8 快 1.78×」也是同样性质的问题——它换的也是整套。

| 组 | torch | kernel 构建 | provider（revision） | 用途 |
|---|---|---|---|---|
| **A** | 2.12 | `…+torch212.bmg` | 0.2.33（`950214ad`） | 已知：int8 稳态 **51.75 s** |
| **B** | 2.13 | `…+torch213.bmg` | 0.2.31（`9eccb7f`） | 只换整套的对照 |
| **C** | **2.12** | `…+torch212.bmg` | **0.2.31** | **分离点：只降 provider** |

- **C 也慢** → 慢的是 **provider 0.2.31 那套代码**（0.2.33 增补的实现才是关键）
- **C 仍快** → 慢的是 **kernel 构建 / torch 版本**，与 provider 无关

C 组技术上可行：`0.2.31` 的 `provider.json` 声明 `torch_version = "2.12.0+xpu"`，
**与 torch 2.12 环境天然匹配**；只需把 `compatible_versions` 补上 `0.2.37`
（本机装的是它），`vendored_files` 的 sha256 随整包搬来**自洽**。
准备脚本 `_stage_provider_031.py`（`prepare` / `verify` / `restore`），
`verify` 会先校验 52 个 vendored 文件的哈希——这是 provider 启动的硬门槛。

### §0.3 ⚠️ 顺带查出：`python_embeded_torch213` 的 provider 声明被改坏了

该环境 `provider.json` 的 `torch_version` 被改成 `2.12.0+xpu`，而它实际装的是 `torch 2.13.0+xpu`
→ OmniXPU 的**字符串相等**校验（`runtime_bootstrap.py`）会**拒绝激活该 provider**，
`import comfy_kitchen` 落到 canonical 0.2.37（签名完整、不崩，但**走不到 XPU 原生路径**）。
同目录 `provider.json.bak` 里是正确的 `2.13.0+xpu`。

→ 已恢复（保留 `compatible_versions` 含 `0.2.37`）。**这条本身就是今晚能跑对照的前提**：
不修的话测的是「provider 被拒 vs provider 激活」，而不是「两套 provider 的差别」。

### §0.5 ⭐⭐ B70 上的同代码对照：**「能力声明」与「内核构建」两项都只值 0%**

同一张 B70、同一套 ComfyUI 代码、同一份 `omni_int8fix.py`、同一分辨率步数
（Qwen-Image 2.1 int8 · 1280×720 · 25 步）：

| 组 | torch / kernel / provider | 开关 | 首轮 | **稳态 ×2** | 均值 | **采样段** |
|---|---|---|---:|---:|---:|---:|
| **b70same** | 2.12 / torch212 / **0.2.33** | 两开关都开 | 52.94 s | 10.61 / 10.64 | **10.62 s** | **9 s** |
| **b70sig** | 2.12 / torch212 / **0.2.33** | 只签名适配 | 46.70 s | 10.65 / 10.67 | **10.66 s** | **9 s** |
| **b70t213** | **2.13 / torch213 / 0.2.31** | 两开关都开 | 38.52 s | 10.59 / 10.67 | **10.63 s** | **9 s** |

**三组稳态落在 10.62 / 10.66 / 10.63 s——极差 0.4%，采样段全部 9 s（1.2 s/步）。**

→ **「能力声明」在 B70 上也只值 0%**（10.62 vs 10.66）。
→ **换整套内核构建（torch + kernel + provider）在 B70 上也只值 0%**（10.62 vs 10.63）。
→ **两卡六组（B50 三组 + B70 三组）全部一致指向同一结论**，见下表：

| 卡 | 「能力声明」值多少 | 「换内核构建」值多少 |
|---|---:|---:|
| **B50**（16 GB） | 4~5%（Krea-2 唯一能量出） | 1.5~3.4% |
| **B70**（32 GB） | **0%** | **0%** |

**⚠️ 首轮差异很大（52.94 / 46.70 / 38.52 s）但稳态几乎相同** ——
首轮受**磁盘缓存与权重落盘顺序**影响，`loads` 计数分别是 3 / 3 / 3，
**首轮不能用来比内核**。这是本项目第一次明确「首轮 vs 稳态」在同代码下的分离。

### §0.6 那1.78× 的归属：**排除法已收敛到 ComfyUI 代码，不是内核、不是能力声明**

| 批次 | 内核构建 | int8fix | ComfyUI 代码 | B70 int8 稳态 |
|---|---|---|---|---:|
| 2026-10-14（`torch213`） | torch213 | **无** | 补丁**前** | 18.85 s |
| 2026-10-15（`torch212`） | torch212 | **有** | 补丁**后**（`ops.py` mtime 10-14 22:43） | 10.63 s |
| **2026-10-17 b70t213（今天实测）** | **torch213** | 有 | **同一份（补丁后）** | **10.63 s** |

**今天这组是决定性的**：它把「内核构建」单独摘出来、其余两项与 10-15 对齐，
结果稳态与 10-15 **逐位相同**（10.59 / 10.67 vs 10.63）。
→ **内核构建这一项对 INT8 速度的贡献 = 0%**（不是 3.4%，B70 上连噪声都不到）。

**再排除「能力声明」**（`b70same` vs `b70sig`）：0%。

→ **1.78× 剩下的唯一候选是 ComfyUI 代码补丁本身**（`ops.py` / `model_management.py`，
mtime 2026-10-14 22:43 落在两批数据采集之间）。
**这一项本项目未做「同代码回退补丁」的对照**（回退会破坏当前可用栈，
风险高于收益）——所以最终定性是：**1.78× 归因于 ComfyUI 代码版本，不是硬件、不是内核构建。**

>📌 **能确定 / 不能确定**：
> - ✅ **确定**：内核构建、provider 版本、能力声明开关，三者对 INT8 速度的贡献在
>   **B50 与 B70 上都是 0~3%**。10-15 那个 1.78× **不能归给任何一项**。
> - ⚠️ **未验证的最后一环**：ComfyUI 代码补丁本身的贡献（需回退补丁做对照，
>   风险高于收益，未做）。
> - 📌 **对外口径**：**不要把 1.78× 说成「换了内核」**。若要讲这一段，
>   只能说「同一张卡上，ComfyUI 0.39 的一个补丁前后差 1.78×，
>   内核构建与 provider 版本的影响在3% 以内」。

⚠️ **本仓库里 2026-10-14 那批 B70 出图记录全部是 `torch213.bmg` + 无 int8fix**，
它们**不能代表「B70 的 int8 能力」**，只能代表「那个内核下的表现」。
引用时必须带 `env.kernel_variant` 与 `env.stack_variant`。

## 一、采集口径

| 项 | 口径 |
|---|---|
| 计时来源 | 服务端 `execution_start` → `execution_success`，**不含排队** |
| 软件栈 | ComfyUI **0.39.0** + `comfy-kitchen 0.2.37` + `omni_xpu_kernel 0.2.0b2+torch213.bmg` |
| 显存 | 31.16 GiB（B70 关 ECC）/ 32 GB 内存 |
| 三种角色 | **`first`** 模型刚换上来（含加载）· **`resident`** 同提示词换种子（稳态）· **`newprompt`** 换提示词（ComfyUI 节点缓存全失效） |
| 采样组 | 每组跑 2 个 resident（检验稳态是否真稳），另 1 个 first + 1 个 newprompt |
| 文本编码器 | **2.1 的 8B 编码器本机只有 int8 版**（无 bf16），三组统一用 `qwen3vl_8b_int8_convrot`——bf16 行只在编码器上有偏差，INT8 行是精确对齐 |
| 启动参数 | 不带 `--enable-dynamic-vram`（0.39 上 aimdo 的 XPU provider 缺 `aimdo_storage_fast_disk`，启用即崩） |

**三种角色不可混比。** `first` 那一轮要付整个模型的加载（Qwen-Image 2.1 bf16 的 DiT
就 13.25 GiB），`resident` 是模型已驻留后的净成本，`newprompt` 介于两者之间（文本编码要重跑）。

## 三、结果

> **读这一章前先看两件事：**
> ① **§3.1–3.3 是一批，§3.3b 是另一次重采。两批不能混着比。** 旧批（§3.1–3.3）采集时间早于本地补丁，
> 表里的「稳态」列在部分配置上包含了模型重装时间，与 §3.3b 的口径不同。
> ② **跨档位比性能只用 `s/it`（采样速率）**；端到端秒数只在 `loads == 0`（模型没被重新装载）时才可比。
> 判据见 §3.3b。

### 3.1 Qwen-Image 2.1 · 1280×720 · 25 步 · cfg 1.0

| DiT 档 | 首轮（含加载） | 稳态 ×2 | 换提示词 | 其中采样（稳态） |
|---|---:|---:|---:|---:|
| `bf16`（13.253 GiB） | 96.66 s | **13.69 / 13.77 s** | 14.31 s | 12 s（**0.48 s/步**） |
| `int8_convrot`（6.758 GiB） | 28.04 s | **18.87 / 18.83 s** | 19.27 s | 17 s（**0.68 s/步**） |

**⚠️ 这张表量的是 `torch213.bmg` 内核 + 无 int8fix 的栈，结论只在该栈成立。**
换 `torch212.bmg` + int8fix 后，int8 稳态 **10.63 s**，比 bf16 **快 23%** —— 见 §0。
下面的「bf16 比 int8 快 37%」是**内核配错**的产物，不是卡的性质。

### 3.2 Krea-2 Turbo · 1024×1024 · 8 步 · cfg 1.0

| DiT 档 | 首轮（含加载） | 稳态 ×2 | 换提示词 | 其中采样（稳态） |
|---|---:|---:|---:|---:|
| `bf16`（24.478 GiB） | 173.74 s | **9.33 / 9.26 s** | 21.70 s | 7 s（**0.88 s/步**） |
| `int8_convrot`（12.566 GiB） | 41.90 s | **11.60 / 11.57 s** | 11.70 s | 9 s（**1.12 s/步**） |

> `bf16` 的「换提示词」是稳态的 2.3 倍（21.70 vs 9.33），`int8` 却几乎不变（11.70 vs 11.60）。
> 原因在容量：**bf16 组合 24.478 + 8.266 + 0.236 = 32.98 GiB，装不进 31.16 GiB 的卡**，
> 所以 bf16 每换一次提示词都要把文本编码器重新搬一遍；int8 组合只有 21.07 GiB，全驻留。

### 3.3 MiniMax Music 3 · 120 s · 30 步 · cfg 1.7

| DiT 档 | 首轮 | 稳态 | 换歌词 | 其中采样（稳态） |
|---|---:|---:|---:|---:|
| `fp16`（4.577 GiB） | 214.40 s | **105.54 s** | 127.90 s | 69 s（**2.30 s/步**） |
| `int8_convrot`（2.330 GiB） | 166.79 s | **163.96 s** | 190.02 s | 131 s（**4.37 s/步**） |

**同样的反常：`fp16` 稳态比 `int8` 快 55%**（同样是 `torch213.bmg` + 无 int8fix 的栈）。机制见第五节。

### 3.3b ⭐⭐ 量化到底带来什么：**三个独立模型都是 29–32%，口径是「采样速率」不是端到端**

上面三张表的「稳态」列混了两种东西：**采样时间**和**模型重载时间**。把它们拆开后，规律才露出来。

> **口径规则（先记住这条）**：跨档位比性能一律用 `s/it`（或 `it/s`，采样速率）。
> **只有 `loads == 0`（模型没被重新装载）时，端到端秒数才有可比性。**

| 模型 | 配置 | 浮点档 `s/it` | int8 档 `s/it` | int8 采样提速 |
|---|---|---:|---:|---:|
| Krea-2 Turbo | B70 · 1280×720 · 8 步 | bf16 **1.165** | **1.543** | **1.32×** |
| Qwen-Image 2.1 | B70 · 1280×720 · 25 步 | bf16 稳态 13.79 s | 10.64 s | **1.30×** |
| MiniMax Music 3 | B70 · 120 s · 30 步 | fp16 DiT **2.30** | **1.79** | **1.29×** |

**三个模型，三条独立采集路径，结论落在 1.29×–1.32× 的同一个区间。**
⚠️ 本节三行来自**同一次重采**（同栈同批，内部可比）；**不能与上面 §3.1–3.3 的旧批次混用**——
后者采集时间早于本地补丁，Music 3 的 int8 采样当时记到 4.37 s/it，现已不是这个值。

⚠️ **但端到端完全可能反过来，原因在显存装不装得下**（这是本节要讲的重点）：

- **Krea-2 bf16**：DiT 24,478 MiB + TE 8,266 MiB = **32,916 MB > 整卡 31,907 MB**
  → 在 B70 上**永远不可能驻留**，每轮都要重装 24 GB → 端到端 115.88 s，是 int8（6.00 s）的 **19 倍**。
  **这 19 倍是「装不装得下」，不是「量化」。**
- **Music 3 int8 DiT**：采样快了 29%，但每轮重载比 fp16 更重（`loads` 3 vs 1）
  → 端到端 **208–220 s，反而比 fp16 的 133 s 慢 60%**。
  **采样更快 ≠ 端到端更快。**

→ **对客口径一句话**：INT8 量化在**采样阶段**稳定省 **29–32%** 时间；
**能不能变成端到端的收益，取决于该组合在卡上驻不驻留**，而驻留与否只由「显存够不够」决定。
所以给客户的建议应该是：**先按显存选档位（选 int8 往往就是为了驻留），再谈量化收益。**

### 3.3c 补一条**能量**证据：装不装得下，功耗表上直接看得见

上面那张 19× 的账有个疑问：「bf16 慢 19 倍，是不是也**多耗 19 倍电**？」
实测答案是否定的 —— **只多 5.6 倍**。因为重装那段时间 GPU 在等磁盘，功率只有 82 W。

| 模型 | 稳态耗时 bf16/fp16 → int8 | 稳态能量/次 bf16/fp16 → int8 | **P90 功率** | 能量收益 |
|---|---|---|---:|---:|
| Qwen-Image 2.1 | 14.05 → 10.80 s（−23.1%） | 4.14 → 3.20 kJ | 291 W / 291 W | **−22.5%** |
| Krea-2 | 127.74 → 6.08 s（−95.2%） | 10.82 → 1.93 kJ | **93 W** / 291 W | **−82.1%** |
| Music 3 | 232.95 → 193.73 s（−16.8%） | 39.16 → 32.74 kJ | 290 W / 290 W | **−16.4%** |

- **前两行的「能量收益 ≈ 时间收益」（差 < 1 个百分点）**：因为两档的 P90 都是 290 W ——
  **量化不改功率，只改耗时**。所以正确的说法是「int8 算得快，所以每次少花电」，
  而不是「int8 更省电」。
- **Krea-2 那一行是唯一的例外，而且它把「装不下」写在了功耗上**：
  bf16 的 **P90 只有 93 W**、占空比 5.6%（卡 94% 的时间在等磁盘）。
  时间差 19×，能量只差 5.6× —— **「装不下」的代价主要在时间，不在电费。**
  → **看到 P90 远低于 290 W，就说明这个配置装不下，不用去翻体积账。**

（0.5 MP → 1.03 MP 像素 2.06×、单步 3.92×，见 [`comfyui-h3.md`](comfyui-h3.md) 第八节）。

**16 GB 档的实际出图上限**：
- **1280×720 与 1536×864 都是 4/4 全通**，日常用 1536×864 没问题（每张约 65 s）。
- **2048×2048 跑得通，但很贵**：稳态单张约 **246 s（4.1 分钟）**，是 1280×720 的 **4.8 倍**
  （像素只多 4.55 倍）。日志里出现 `VAE decode: low XPU VRAM (6.8GiB free) — releasing
  other models first`，解码阶段要先把别的模型请下去。
- ⚠️ **再往上（2.1 支持到更高）本项目未测，不给数字。**

#### 3.4.0b ⭐⭐ Krea-2 的完整 2×2：**「能力声明」在本机只值 4~5%，不是 −40%**

同一张 B50、同一套代码、同一分辨率步数（Krea-2 Turbo 1024×1024 · 8 步），
把「能力声明」与「签名适配」两格都跑全：

| 配置 | `Native ops`（启动日志实测） | 首轮 | **稳态 ×2** | 换提示词 |
|---|---|---:|---:|---:|
| **base**（两个开关都关，shim 完全不装） | `int8_tensorwise`（其余 emulated） | 85.62 s | 62.67 / 59.70 | 60.67 s |
| **sigfix**（能力声明关 + 签名适配开） | `int8_tensorwise`（其余 emulated） | 85.08 s | 63.86 / 60.11 | 58.12 s |
| **int8fix**（两个都开） | **四个全 Native** | 86.88 s | **58.47 / 57.30** | **58.03 s** |

**⭐ 这张表解释了一个此前未解的异常**：ComfyUI 的
`get_disabled_quant_formats()` 是**四个格式同生同死**（`if not supports_int8_compute:`
一次性 add `int8_tensorwise` + `convrot_w4a4` + 两个 grouped）。
但 base 格（**门禁全关、shim 根本没装**）的日志却是
`Native ops: int8_tensorwise , emulated ops: … convrot_w4a4, asym_w4a8_int8, w6a8_int8 …`
—— **只有一个在 Native**。
→ **是 OmniXPU 的 `int8_ffn_adapter` 把 `int8_tensorwise` 独立加回了 native，绕过了 ComfyUI 的门禁。**

**两条结论：**

1. **签名适配对 Krea-2 无用**（base 61.19 vs sigfix 61.99，差 1.3%，在噪声内）——
   符合预期：Krea-2 的模型前向不调 `comfy.ops.linear_input_act`，
   撞不到 12 参 vs 8 参那个签名错配。
2. **能力声明对 Krea-2 只值 4~5%**（稳态 61.19 → 57.89；换提示词 60.67 → 58.03）。
   **⚠️ 与 B70 那批「−40%」差了一个数量级。**

> 📌 **这意味着「翻能力声明 = 快 40%」不是普适结论，它依赖具体环境**
> （本机 B50 · torch212 内核 · 当前 ComfyUI 代码上测不出来）。
> **对外只说「需要打开 INT8 原生路径」，不要承诺具体百分比**，
> 百分比必须由「同卡同栈的对照」给出，而那需要在目标机器上实测。

**⚠️ 也因此，「基线格」在 Qwen-Image 2.1 上打不开**（会撞签名错配而崩），
**只有在 Krea-2 这种不走该路径的模型上才能量到「反量化 vs 原生」**——
而一量出来就是 4~5%，不是 40%。

#### 3.4.0e ⭐⭐ KV 缓存（`QwenImage21Cache`）：**稳态完全不受它影响**

上游 `QwenImage21Cache` 有两个维度此前**从未被测过**：`device`
（`auto` / `gpu` / `cpu` / `off`）与 `dtype`（`default` / `int8` / `int4`）。
上游tooltip 自己写着：*「`off` 每步重算前缀、更慢，**但它是排除缓存影响的唯一办法**」*
→ 那就用它来排除。

同一张 B70、同一套代码、Qwen-Image 2.1 int8 · 1280×720 · 25 步，各 4 轮：

| `device` / `dtype` | 首轮 | **resident ×2** | 换提示词 |
|---|---:|---:|---:|
| `auto` / `default`（历史默认，基线） | 27.11 s | **10.85 / 10.70** | 11.04 s |
| **`gpu` / `default`** | 50.86 s | **10.63 / 10.65** | 11.02 s |
| **`cpu` / `default`** | 27.14 s | **10.77 / 10.75** | 11.13 s |
| **`off` / `default`**（= 关掉缓存） | 26.98 s | **10.61 / 10.60** | 11.00 s |
| `auto` / **`int8`** | 27.82 s | **10.68 / 10.69** | 11.12 s |
| `auto` / **`int4`** | 29.08 s | **10.72 / 10.72** | 11.14 s |

**⭐ 核心结论：`off` 与 `auto` 的稳态逐位相同（10.61/10.60 vs 10.61/10.64）。**

→ **在这个负载下，KV 缓存压根没起作用**：把它整个关掉（每步重算前缀）**一点不变慢**。
**机制**：模型驻留后每步只做一次 DiT 前向，而 Qwen-Image 2.1 是 25 步，
每步的计算量相对于「重算文本前缀」大得多 → **前缀缓存的收益被采样淹没**
（出图侧本来就是**计算主导**：采样占稳态 56~90%）。

→ **调 `device` / `dtype` 对出图速度没有意义**，对客与调优都不用碰。
→ ⚠️ 但**这个结论只对「模型驻留 + 采样主导」成立**；若工作负载变成
**长文本 prefix + 少步数**（如编辑类工作流），缓存才可能显出来——**那种场景本项目未测**。

⚠️ **首轮那一列（50.86 / 27.14 / 26.98 / 27.82 / 29.08）不要当成「device 的影响」。**
⭐ **这一点已实测验证**：`auto` 基线那组因工具重跑被追加了三次，
**同配置的三次首轮分别是 51.29 / 27.11 / 27.70 s**（稳态都是 10.6~10.9）
→ **首轮差 24 s 完全由「磁盘页缓存冷热」造成，与 `device` 设置无关。**
判据：**任何跨批次的「首轮」比较都不可信，除非两批的页缓存状态相同。**
（本项目的取法：每组跑 4 轮、只看 resident，且跨批次结论只用稳态。）


#### 3.4.0f ⭐⭐ Krea-2 的 2×2 **跨卡一致**：B70 上「能力声明」也值 0%

同一套 ComfyUI 代码、同一份 `omni_int8fix.py`，两张卡各跑 Krea-2 的完整 2×2
（Krea-2 **不走签名那条路径**，所以 `base` 格能跑 → 唯一能量出
「反量化 vs 原生」直接对照的模型）：

| 卡 | `base`（两开关全关） | `sigfix`（只签名适配） | `int8fix`（都开） | **「能力声明」值多少** |
|---|---:|---:|---:|---:|
| **B50**（16 GB） | 61.19 s | 61.99 s | **57.89 s** | **4~5%** |
| **B70**（32 GB） | **6.04 s** | 6.07 s | **6.04 s** | **0%** |

（B50 是 2026-10-16 的数据；B70 是 2026-10-17 同代码复测。）

**⭐ 两条结论：**

**① 「能力声明」的收益跨卡一致地很小（B50 4~5% · B70 0%），跨卡合起来 ≤5%。**
再叠上 Qwen-Image 2.1 的 ≈0% 与 Music 3 的 2%，
→ **四个模型 × 两张卡，「能力声明」全部 ≤5%**。
⚠️ **再次确认：对外不要承诺「打开 INT8 原生路径快 40%」**，
只讲机制（不翻这处判定，INT8 权重就被反量化回浮点算）。

**② ⭐⭐ B70 比 B50 快 9.6×（6.04 vs 57.89 s），这是本项目目前最大的跨卡倍数。**
与 Qwen-Image 2.1 的 4.87× 相比，Krea-2 的倍数大得多
→ **不是因为卡更慢，而是负载形态不同**：Krea-2 的 DiT 有 **12.57 GiB**，
在 B50 上虽能完整驻留但**固定开销 42 s**（采样只有 16 s，**加载主导**）；
B70 上显存充裕、这42 s 直接消失 → **倍数被「加载主导 × 容量受限」放大了**。
**这条是对客最有说服力的一条**：*「同样的模型，16 GB 卡上 58 秒、32 GB 卡上 6 秒——
差别不在芯片，在你要不要为了容量去挤 16 GB。」*
⚠️ **两格分辨率不同**（B50 那批是 1024×1024，B70 这格是 1280×720）→ **「差一个数量级」的方向成立，
但不能当精确倍数引用**（像素只差 14%，解释不了 10 倍）。

#### 3.4.0g ⭐ Krea-2 的分辨率维度（B70）

Krea-2 此前只有 1024×1024 一点（那是 B50 那批）。下表是 B70 · int8 · 8 步，从 1280×720 起的三个点：

| 分辨率 | 像素 | 像素比 | 稳态 ×2 | 均值 | **时间比** | 换提示词 |
|---|---:|---:|---:|---:|---:|---:|

#### 3.4.0c ⭐⭐⭐ 三模型汇总：**「能力声明」的收益在 B50 上全部 ≤5%**

同一张 B50、同一套 ComfyUI 代码、同一份 `omni_int8fix.py`，三个模型各跑自己的 2×2：

| 模型 | base<br>（两开关全关） | sigfix<br>（只签名适配） | int8fix<br>（两个都开） | **能力声明值多少** |
|---|---|---|---|---|
| **Qwen-Image 2.1** | ❌ **0/4 全崩**（签名错配） | ✅ 4/4 · 稳态 47.68 | ✅ 4/4 · 稳态 51.75 | **≈ 0%**（采样段逐位相同） |
| **Krea-2 Turbo** | ✅ 4/4 · 稳态 61.19 | ✅ 4/4 · 稳态 61.99 | ✅ 4/4 · 稳态 57.89 | **4~5%** |
| **Music 3**（int8 TE） | ❌ **崩**（签名错配） | ✅ 2/3 · 稳态 221.81 | ✅ 2/3 · 稳态 216.82 | **2%** |

**这张表是本项目关于 INT8 的最重要的一张表**，三个要点：

1. **「签名适配」决定能不能跑。** Qwen-Image 2.1 与 Music 3 在 base 格全崩
   （`TypeError: int8_linear() got an unexpected keyword argument 'input_act_weight'`），
   装了适配层就 4/4 通过。**这不是可选项。**
2. **「能力声明」的收益在三个模型上全部 ≤5%。** Krea-2 的 4~5% 是唯一能量出来的
   「反量化 → 原生」直接对照（只有它不走签名那条路径，base 格才打得开）。
3. **⚠️ 因此，B70 那批的「Krea-2 / Music 3 快 40%」在本机复现不出来。**
   最可能的解释：**OmniXPU 的 `int8_ffn_adapter` 已经独立把 `int8_tensorwise`
   注册成 native，绕过了 ComfyUI 那道门禁**（base 格的 `Native ops` 里
   `int8_tensorwise` 单独在列，而门禁是四个格式同生同死——只有 adapter 能造成这种局面）。
   **在装了这个 adapter 的环境里，「关掉门禁」本来就不值钱。**
   那个 40% 究竟来自什么（不同 kernel / 不同 ComfyUI 代码 / 别的），**需要 B70 复测才能定**。

> 📌 **对外口径（重要）**：**不要承诺「打开 INT8 原生路径能快 40%」。**
> 本机可复现的说法是：
> - 「INT8 必须走原生路径，否则权重被反量化回浮点算」——**机制陈述，成立**；
> - 「具体快多少要在你这台机器上量」——**百分比不给，因为实测跨机器差一个数量级**。

## 四、出图与出视频的根本差别：一个是计算主导，一个是加载主导

把 `resident` 轮的采样段和固定开销拆开（`timing_breakdown`，由日志取证回填）：

| 工作负载 | 分辨率 | 角色 | 采样占端到端 | 固定开销 |
|---|---|---|---:|---:|
| **出图** Qwen-Image 2.1 int8 | 1280×720 | resident | **90%** | 1.8 ~ 1.9 s |
| **出图** Krea-2 int8 | 1024×1024 | resident | 78% | 2.6 s |
| **出图** Qwen-Image 2.1 int8 | 1280×720 | first（含加载） | 61% | 11.0 s |
| **出图** Qwen-Image 2.1 bf16 | 1280×720 | first（含加载） | 16% | 81.7 s |
| **出视频** MiniMax H3（B70） | 864×480 | fresh | 14 ~ 16% | 227 ~ 275 s |
| **出视频** MiniMax H3（B50） | 864×480 | fresh | 41% | 234.5 s |

> 两个 `first` 行的差别本身就是结论：同样是「模型刚换上来」，
> **int8 档 11.0 s 就把 6.76 GiB 装完了，bf16 档要 81.7 s 才装完 13.25 GiB**——
> 加载时间大致跟着权重体积走。而 resident 一轮的固定开销只剩 1.8 s。
> 所以出图这条线上「第一个 prompt 慢、后面快」的落差比 H3 更陡（7 倍 vs 1.2 倍）。

→ **H3 视频在 32 GB 档上是「加载主导」（旧栈固定开销 87~95%，10-19 那批 74%），调步数收益小；
出图是「计算主导」（模型已驻留时采样占 78~90%），调步数直接按比例见效。**
两者的优化方向是反的，别把视频那套结论套到出图上。

> 另一个数字上的差别：出图的稳态是**十几秒**量级，出视频是**几分钟**量级——
> 因为出图模型小一个数量级（6.8~12.6 GiB 的 DiT vs H3 的 19.53 GiB），
> 而且没有 5 秒视频要解的那一串帧。

## 五、⚠️ ComfyUI 0.39 里有一行把 Intel XPU 判为「不支持原生 INT8」

> **来源分层（别读成「Intel 官方说 XPU 不支持 INT8」）**：
> 这行代码出自 **ComfyUI 上游 PR #16130**（commit `313a76fb8`，2026-09-08，
> 作者 Jialong(Bruce) Li），**本机与上游 HEAD 逐字节一致，不是本机改的**。
> 该 commit 的注释**只解释了 MPS 的动机，没说为什么把 XPU 一起关掉**。
> **同一套硬件在 ComfyUI 0.34（秋叶生产栈）上没有这道门禁**，int8 天然走原生
> （启动日志 `Native ops: convrot_w4a4, asym_w4a8_int8, int8_tensorwise`）。
> 完整出处与 0.34 对照见 [`comfyui-capability.md`](comfyui-capability.md) §3.2。

这是本项目在出图这条线上挖到的最值钱的一条。

ComfyUI 0.39 的 `comfy/model_management.py`：

```python
def supports_int8_compute(device=None):
    ...
    if is_intel_xpu():
        return False          # ← 硬编码：Intel XPU 一律当作「不原生支持 INT8」
    ...
    return True
```

后果在 `comfy/ops.py: get_disabled_quant_formats`：`int8_tensorwise` 与 `convrot_w4a4`
被塞进 disabled 集合，启动日志变成 `Native ops: , emulated ops: int8_tensorwise, convrot_w4a4`——
也就是 **INT8 权重被反量化回浮点再算，比纯 bf16 还慢**。

把这一处判定翻过来（`OMNIXPU_INT8_COMPUTE=1`）之后：

| 组 | INT8 原始 | 打补丁后 | 变化 | 本机 0.39 上能跑吗 |
|---|---:|---:|---|---|
| **Krea-2 Turbo** int8 · 换提示词 | 11.70 s | **7.07 s** | **−40%**¹ | ✅ |
| **Music 3** int8 · 换歌词 | 190.02 s | **114.74 s** | **−40%**¹ | ✅ |

⚠️¹ **这两个百分比不可移植。** 同一台机器的 **B50**（torch212 内核 · 当前代码）上，
Krea-2 的完整 2×2 对照显示「能力声明」**只值 4~5%**（§3.4.0b）——差一个数量级。
机制：OmniXPU 的 `int8_ffn_adapter` 已独立把 `int8_tensorwise` 注册为 native，
**绕过**了 ComfyUI 那道门禁，所以门禁在装了 adapter 的环境里本就不太值钱。
→ **对外只讲机制，不承诺百分比。**
| **Qwen-Image 2.1** int8 | 19.27 s | 无可测收益² | ≈ 0%（开关层面） | ✅ B50 4/4 通过 |

² 「无可测收益」指的是**能力声明开关**对它无收益（见 3.4.1 的 2×2）；
但与同卡同栈的 `bf16` 对照，`int8` 快 **36~41%**（见 3.4）——那是量化本身加原生路径的功劳，
不是这个开关的功劳。B70 上该组的 int8fix 记录是 `discarded`（0/4），未在 B70 上复现。
**三行不能横向比**（列的都是「换提示词/换歌词」这一角色，但走的路径不同）：
Krea-2 / Music 3 是「翻开关直接生效」；Qwen-Image 2.1 还需要下面这件**独立的事**才能跑通。

Qwen-Image 2.1 当初 4 次全失败，报错很具体：

```
TypeError: int8_linear() got an unexpected keyword argument 'input_act_weight'
```

**根因（已定位到行，已修复并端到端实测）**：ComfyUI 0.39 的 `comfy/ops.py:1028` 按 **12 参契约**调用
`ck.int8_linear`（多传 `input_act_weight` / `input_act_eps` / `residual` / `residual_scale`），
而 `comfy_kitchen_xpu_runtime` 里 vendored 的那份 `comfy_kitchen` 是 **0.2.31/0.2.33 快照**，
其 `int8_linear` 只有 **8 参** → 多出来的关键字直接 TypeError。

**这是签名不匹配，不是功能缺口。** XPU kernel 的融合激活白名单是
`(None, "none", "gelu_tanh", "swiglu")`——**含 `swiglu`**，而 Qwen-Image 2.1 的调用点
（`comfy/ldm/qwen_image21/model.py:65`）传的正是 `"swiglu"`。
而被丢掉的 4 个参数在那条调用路径上**本来就是空值**
（`linear_input_act(linear, x, "swiglu")` 只给 3 个位置参数 ⇒ `act_weight=None`、`act_eps=0.0`、
`residual=None`），只有 pre-norm block 才会用到。**⇒ 适配后语义完全等价、零性能代价。**

| 模型 | 模型前向是否走融合路径 | 打 int8fix 后 |
|---|---|---|
| Krea-2 Turbo / Music 3 | 否（各自的 MLP 不调 `linear_input_act`） | ✅ 直接吃到 −40% |
| **Qwen-Image 2.1** | 是（MLP 的 `[gate;up]` 融合） | ✅ 签名适配后 4/4 通过；**速度收益 ≈ 0** |

### 5.1 为什么 Qwen-Image 2.1 拿不到那 40%

启动日志的 `Native ops` 一行是答案：

| 配置 | `Native ops` | `emulated ops` |
|---|---|---|
| 能力声明**关** | `int8_tensorwise` | `nvfp4, float8_*, mxfp8, asym_w4a8_int8, w6a8_int8, convrot_w4a4` |
| 能力声明**开** | `asym_w4a8_int8, w6a8_int8, int8_tensorwise, convrot_w4a4` | `mxfp8, nvfp4, float8_*` |

**`int8_tensorwise` 在两种状态下都是 Native。** Qwen-Image 2.1 的 int8 权重正是这个格式
→ 它**无论开关如何都走原生 kernel**，所以「翻开关」对它**没有可解锁的东西**。
Krea-2 / Music 3 受益的是 `convrot_w4a4` / `w6a8_int8` / `asym_w4a8_int8`
这三格从 emulated 转 native，那才是 40% 的来源。

> 实测印证（B50，3.4 节 2×2）：两组采样段**逐位相同** 29 s · 1.16 s/步。
> → **对 Qwen-Image 2.1，签名适配决定能不能跑，能力声明不决定快不快。**

### 5.2 修复方式（两种，已端到端实测第一种）

| 方式 | 做法 | 状态 |
|---|---|---|
| **A · 适配层（推荐，已验证）** | 在 provider 之外包一层：认得 `gelu_tanh`/`swiglu` 原样透传保住融合；不认的字面量（如 `rms_norm`）先 eager 算完再以 `input_act=None` 交给 kernel；`residual` 用 `torch.addcmul` 外部补 | ✅ **B50 上 4/4 端到端跑通**（74.93 / 47.93 / 47.42 / 46.95 s）；数值侧最小验证 cosine **0.9997**、相对 L2 误差 2.43% |
| **B · 升级 provider（长期正解）** | 上游 `xiangyuT/comfy-kitchen-xpu` 的 PR #12「Sync Kitchen 0.2.37 and add native XPU INT8 linear for W4/W6」（2026-10-09 合入，+8778 / −1458，52 文件）已把签名补齐并加了原生 W4/W6 路径 | ⏳ 待装包（**不在公共 PyPI**，需向内核提供方取） |

> **不能直接改 vendored 文件**：`provider.json` 的 `vendored_files` 对每个文件做 sha256 校验，
> 改一个字节就会 `vendored provider file hash mismatch` 启动失败。适配只能落在 provider 之外的运行时。

> **适配层实现**：`ComfyUI/custom_nodes/omni_int8fix.py`，两处开关**已解耦**——
> `OMNIXPU_INT8_COMPUTE` 管能力声明、`OMNIXPU_INT8_SIGFIX` 管签名适配
>（解耦是为了能把「能不能跑」与「快多少」分开量，见 3.4 的 2×2）。
> 诊断工具：`bench/harness/probe_int8_kernel.py`（复现崩溃 → 装适配层 → 对 cosine）。
> 数据：`bench/data/2026-10-14_b70-32g_*-int8fix-comfyui.json` 与
> `bench/data/2026-10-16_b50-16g_qwen-image-2.1-*.json`，
> `env.stack_variant` ∈ {`int8fix`, `sigfix`}，**不可与基线并排引用**。
