# Test Item Registry

> **The master ledger for every test item in this repository.** One stable ID per item: what was tested, which card it ran on, where the data lives, where the conclusion lives, how to reproduce it — all on one page.
>
> **B60 / B65: fill in the same table when the cards arrive** — no new structure, no renumbering, no change to the definitions. To change a definition, edit this registry first and state why; historical numbers are voided and re-measured per the rules in `bench/README.md`.

After the push, every file was checked against its git blob sha: **289/289 match local exactly** (`.gitattributes` `* -text` took effect, so the byte-level log evidence survived line-ending conversion).

## 0. ID and status rules

| Prefix | Meaning |
|---|---|
| `T-xx` | Test item (one question to answer) |
| `H-xx` | Harness (script under `bench/harness/`) |
| `D-xx` | Data file batch (`bench/data/*.json`, split by schema) |

| Status | Meaning |
|---|---|
| ⛔ Not tested | Never run |
| 🔵 In progress | Started, no conclusion yet |
| ✅ Done | **All four parts present**: definition, data JSON, documented conclusion, reproduce command |
| 🟡 First pass | Ran, but the sample is too small or only some cards were covered; registered only, not in the baseline table |
| ↩️ Withdrawn | Produced numbers, later shown invalid; kept on file as a cautionary record |
| ⏸️ Blocked | A prerequisite is missing (hardware not here, environment not built) |

**IDs are permanent and never reordered.** If an item is withdrawn or changes method, keep the ID, change the status, write the reason in the remarks.

**Run the audit after every collection run** (counts, schema, tool coverage; 30 seconds):

```bash
python bench/harness/registry_audit.py
```

### Power fields (from 2026-10-19, H-25)

`summary.power` and `samples[].power`. **`null` = not collected, not 0 W** —
batches from before the collection capability went live are necessarily `null`, and power cannot be backfilled after the fact.

| Field | Meaning | When to look at it |
|---|---|---|
| `card_domain` / `card_limit_mw` | whole-card power-domain index and its power limit (B70 = `1` / `290000 mW`) | confirm that "the whole card is being measured, not one partition" |
| `avg_w` / `energy_j` | **whole-round** average power and total energy, **including model load, offload and VAE decode** | electricity cost, "how many joules one task costs" |
| `p90_w` | the power that 90% of the 1 s windows stay at or below | **this, not `avg_w`, tells you whether the card was pinned** |
| `peak_w` | 1 s window peak (**not** an oscilloscope instantaneous peak) | transient headroom for the PSU and cooling |
| `busy_share` | share of 1 s windows in the whole round at ≥ 80% of the power limit | for load-dominated tiers this alone says how much work the card actually did |
| `counter_resets` | how many times the whole-card domain energy counter **wrapped to zero** (the counter resets mid-run) | `>0` means that window saw a reset. Power is integrated from per-sample deltas and is unaffected, but the count must be visible to know whether the segment can be trusted. **Unavailable is `null`, not 0** |

> ⚠️ **`avg_w` is diluted by the loading segment**: the 864×480 cold round has `avg_w` = 135.0 W and `p90_w` = **290.1 W**,
> because only 28% of the 1 s windows across those 182.6 s are at full load (the rest is loading / decode).
> Using `avg_w` as "full-load power" **underestimates by more than half**.
> The reverse holds too: Krea-2 bf16 reloads every round, `avg_w` = 82.4 W and `p90_w` = **93.1 W** —
> here **even P90 is low**, which says the configuration **never got the card going** (it does not fit).

> 🔴 **A pitfall specific to dual-card machines (2026-10-23)**: `power_sampler.py` only samples Sysman's
> **device 0**, and Sysman device order is **≠** `level_zero:N`. On this machine Sysman dev0 = bus 16 = **card 1**,
> so a batch where "H3 runs on card 0" actually sampled **card 1's idle 42 to 46 W** — the numbers are real, the **attribution is wrong**.
> Use `power_probe_multi.py` (H-26, the CSV carries the PCI bus number) for all dual-card power work;
> `summary.power` in `2026-10-23_h3_1280x720_duald*.json` is already marked `usable: false`, **do not quote the watt figures from it**.
